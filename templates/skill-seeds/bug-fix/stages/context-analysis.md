# Context Analysis（上下文分析）

## ⛔ 强制执行规则

**执行本阶段前，必须先读取并遵守 @references/rules.md 中的红线规则**，特别是：

1. **信息处理红线**：
   - 不允许猜测业务逻辑
   - 不允许假设用户意图、数据格式、环境配置
2. **流程执行红线**：只做本阶段定义的操作，禁止做额外的事

**违反以上规则 = 流程失败**

---

## 任务

基于问题位置，按需加载代码、文档、调用链等相关信息。

---

## 输入

来自问题标准化：
- 问题位置
- 异常信息
- 复现条件

---

## 执行流程

### 1. 定位问题代码

根据问题位置和异常信息，定位代码文件和行号。

### 2. 分析代码实现

读取问题代码，识别：
- 代码执行逻辑
- 涉及的技术点（数据库/缓存/消息队列/外部服务/并发/事务）
- 可能的问题点

### 3. 按需加载文档

根据代码分析结果，按需加载：

**项目文档**（`.harness/wiki/`、`docs/`、`doc/`）：
- 仅加载与问题模块相关的文档
- 不存在则跳过

**中间件文档**（`.harness/wiki/middleware/`）：
- 代码用了什么就加载什么
- 不预先加载所有

### 4. 分析调用链

使用 Grep 工具：
- 搜索函数名/接口路径 → 找上游调用方
- 分析 import 语句 → 找下游依赖

仅分析与问题相关的调用链路。

### 5. 按需分析数据流

**触发条件**：代码涉及数据处理（数据库读写/数据转换/外部数据获取）

分析数据来源、流转、存储。

---

## 截止条件

### 成功
- 已定位问题代码
- 已分析代码实现
- 已按需加载文档（不存在可接受）
- 已分析调用链

### 失败
- 无法定位问题代码 → 结束本流程，回到主流程"问题分析"阶段
- 无法获取任何上下文 → 记录缺失，基于已有信息继续

---

## 输出

**格式**：Markdown 结构化报告

```markdown
# 上下文分析报告

## 问题代码
- 文件：{路径}:{行号}
- 模块：{业务模块}
- 执行逻辑：{代码如何执行}
- 涉及技术：{数据库/缓存/消息队列等}
- 可能问题：{初步判断}

## 调用链
- 上游：{调用方}
- 下游：{依赖方}
- 链路图：{Mermaid 图}

## 相关文档（按需）
- 项目文档：{已加载的内容或"不存在"}
- 中间件文档：{已加载的内容或"不涉及"}

## 数据流（按需）
- 来源：{数据来源}
- 流转：{数据流转路径}
- 存储：{数据存储位置}

## 并发/事务（按需）
- 场景：{并发场景}
- 事务：{事务范围}
- 风险：{潜在风险}

## 下一步
进入"问题认证"阶段。
```

---

## 执行要点

1. **按需加载**：用到什么加载什么，不预先加载所有
2. **逐步深入**：先分析代码，再根据代码情况加载文档
3. **记录缺失**：文档不存在时记录，不影响流程继续
4. **简洁输出**：输出完整但简洁的报告，便于下一阶段使用
