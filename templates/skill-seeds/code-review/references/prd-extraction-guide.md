# PRD 解构指南

把 PRD 文档拆成可对照代码核查的原子需求点。Step 2 PRD 解构动作据此执行。

---

## 一、识别 PRD 结构

读完 PRD 后先判断主结构，决定主提取策略：

| 结构特征 | 主策略 |
|----------|--------|
| 需求表格（含字段名/规则/必填） | 表格驱动：每行一个需求点 |
| 流程描述（步骤 1/2/3 或泳道图） | 流程驱动：每步一个需求点 |
| 用户故事（As a... I want... So that...） | 故事驱动：每个 Acceptance Criteria 一个需求点 |
| 接口契约 / 字段规约 | 字段驱动：每个字段/接口一个需求点 |
| 混合 | 分章节套用，主章节优先 |

---

## 二、原子化拆分

一个需求点 = 一件**独立可验证**的事。粒度判断：

- 太粗 ❌：「实现登录功能」（无法定位代码、无法验态）
- 太细 ❌：「校验手机号长度等于 11」（应并入"手机号格式校验"）
- 合适 ✅：「登录成功后写入 JWT 到 HttpOnly Cookie，过期 7 天」

拆分启发式：

- "并且" / "同时" → 通常应拆为多条
- "如果...则..." → 主路径与异常分支分别成条
- 字段列表（5 个以上）→ 一条覆盖整组，验收点中列字段

---

## 三、字段填充规则

按 [`templates/requirement-list.md`](../templates/requirement-list.md) 最小字段填充：

| 字段 | 填充原则 |
|------|---------|
| `ID` | `R001`、`R002`...连续编号 |
| `需求点` | 一句话主谓宾，不超过 30 字 |
| `PRD 原文` | 引文片段（>100 字时摘要 + `...`），缺失则填「无」 |
| `优先级` | 优先沿用 PRD 标注；无标注则按业务影响推断（核心路径 P0 / 主要功能 P1 / 体验优化 P2） |
| `验收点` | 代码层面**可检验**的原子条件。每条需可对应到具体函数 / 字段 / 配置 |
| `备注` | 人工修正记录、待澄清项、依赖说明 |

数据库扩展字段按 [`templates/requirement-list.md`](../templates/requirement-list.md) 填充。旧版清单没有这些字段时不阻塞，后续由 Step 4.3 从 diff 反扫补充或提示。

**验收点反例**：
- ❌「用户体验良好」（不可检验）
- ❌「性能符合预期」（无具体指标）

**验收点正例**：
- ✅「`LoginController#login` 入参 `phone` 为空时返回错误码 `LOGIN_001`」
- ✅「JWT 过期时间配置项 `auth.jwt.expire-days = 7`」

## 四、典型 PRD 元素映射

| PRD 元素 | 拆解方式 |
|----------|----------|
| 字段表（字段/类型/必填/默认值） | 整张表合并为一条「XX 字段集合」需求，验收点逐字段列出 |
| 异常码定义 | 每个异常码一条，验收点为"在 X 场景返回 Y 异常码" |
| 状态机流转 | 每个状态转移一条，验收点含起始态 / 触发条件 / 终态 |
| 性能指标（QPS/RT） | 单独一条，备注标注"需压测验证，本 review 仅检查代码层面是否有明显瓶颈" |
| 流程图 / 时序图 | 拆为步骤后整理，复杂分支标注「需人工核对」 |
| 截图 / UI 稿 | 标注「需人工核对」，不做代码级验态 |

## 五、需要主动询问用户的情况

以下情形不要硬编一个状态，而是在 `requirements-{ts}.md` 中标注后产出报告，让用户决定：

- PRD 表述模糊（如"合理的过期时间"）
- 多份 PRD / 多个版本之间冲突
- 隐含依赖外部系统但 PRD 未指明对接方
- 缺关键字段类型 / 取值范围

报告中通过 `备注` 字段醒目提示，不阻塞流程。

## 六、数据库需求识别

只要 PRD 或代码变更涉及字段新增/修改、数据库表新增/修改、Mapper/DAO/Repository 的增删改查、SQL/XML 变更、DO/Entity/DataObject 字段变更，就必须进入数据库变更评估。

### 6.1 触发关键词

**Schema 变更强信号**：新增字段、新增表、新增索引、删除字段、修改字段类型、修改字段长度、需要存储、需要持久化、数据落库、表结构变更。

**CRUD 弱信号**：列表查询、详情接口、后台搜索、数据导出、增加/删除/修改某业务实体。命中弱信号时若能从代码或上下文判断其对应数据库表，按数据库变更处理。

**维度/索引强信号**：PRD 提到统计维度、聚合维度、唯一性维度、幂等维度、分组维度、排序维度，且这些维度会参与落库、更新、查询或去重时，必须按数据库相关需求处理。尤其是 `门店 / 商家 / 渠道 / SKU / SPU / 日期` 这类维度，一旦对应 DDL 的唯一键或索引列，需求清单必须填 `数据库变更=是`、补 `关联表`，否则 Step 4.3 容易漏掉 SQL 与索引/唯一键的匹配问题。

### 6.2 字段填充动作

命中数据库相关需求时：

1. `数据库变更` 填 `是`
2. `关联表`：优先提取 PRD 明确表名；只有业务概念时先填 `未知` 或候选表名
3. `PRD 表结构来源`：PRD 中有 DDL 或结构摘要则填章节；没有则填 `缺失`
4. `审查使用的 schema 来源`：可记录 PRD 章节、项目 SQL/DDL 文件、迁移目录或 `无`

PRD 中必须提供相关表结构。完整度标准见 [`templates/requirement-list.md`](../templates/requirement-list.md) 的「数据库物料完整性判定」。如果缺失，不要阻塞 PRD 解构，但必须在最终报告中指出并建议补充后复审。
