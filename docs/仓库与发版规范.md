# agent-desk 仓库与发版规范

本文约定 **agent-desk** 的分支、版本、发版与排查方式。目标：已发布/已交付的版本号能在 Git 里精确还原，避免「本地 main 已超前、对不上现场」。设计与实现均按本文执行。

---

## 1. 模型概览

```text
feature/fix 分支 ──► 合并进 main ──► bump 版本（如需要）──► commit
                                              │
                                              ▼
                                    发版并打 annotated tag
                                    stable: v{version}
                                    预发/测试: v{version}-beta（如需要）
```

| 概念 | 约定 |
|------|------|
| 集成线 | `main`（日常合入）；**main ≠ 已发布** |
| 已发布快照 | Git **annotated tag**，与根目录 `package.json` 的 `version` 对应 |
| 开发方式 | 功能/修复在独立分支完成，再合入 `main`，在 `main` 上发版打 tag |

不强制长期 `release/*`、`develop` 双线；以 **main + tag + 按需 hotfix** 即可。

---

## 2. 版本与 Tag

- 版本号：以仓库根 `package.json` 的 `version` 为准（当前为 monorepo 顶层版本）；发版前与 CHANGELOG（若有）对齐。
- Tag 命名：
  - **正式**：`v{version}`，例如 `v0.1.0`
  - **预发/测试**（若使用）：`v{version}-beta`，例如 `v0.1.0-beta`
- Tag 打在发版时的 **已提交 HEAD**（不含未提交改动）。发版前必须先 commit。
- Tag 默认先打在本地，再 `git push origin v{version}`（或你们约定的推送方式）。
- 按版本排查、热修：见 **§5**、**§6**。

示例：

```bash
# 版本已写入 package.json 并 commit 后
git tag -a "v0.1.0" -m "agent-desk 0.1.0"
git push origin v0.1.0
```

---

## 3. 日常开发

1. 从最新 `main` 拉功能/修复分支（`feature/…`、`fix/…`）。
2. 按业务/功能拆分 commit，避免无关改动混在同一提交。
3. 开发完成后 **merge（或 PR 合入）`main`**。
4. 在 **`main` 上** bump 版本（如需要）、写说明、commit，再打 tag / 发版。
5. 发完后推送 `main` 与相关 tag，便于他人协作与按版本还原。

说明：IDE 里把 `fix/B2026…` 收成「fix 文件夹」，只是按分支名里的 `/` **分组展示**，**不是** git worktree。是否有额外工作区以 `git worktree list` 为准。

---

## 4. 发版要点

1. 确认要发布的改动均已在 `main` 且已 commit。
2. 对齐 `package.json` 版本与发布说明。
3. 执行项目约定的构建/发布步骤（如 `pnpm build`、发布产物等）。
4. 打 annotated tag 并推送到远程。
5. 若同一版本先打了 `v*-beta` 再升正式：可再打 `v{version}`；**勿假设** artifact 仓库允许同号重复上传——若产物库同版本不可覆盖，正式通道只改标记/配置、不再传同号包。

---

## 5. 旧版本热修

用户或环境仍停留在旧版、且短期无法强制升级时：从**出问题的 tag** 拉修复分支，不要长期停在 detached HEAD 上改。

```text
v0.1.0 ──► 分支 fix/… 或 hotfix/… ──► bump 补丁号 ──► 发版并打新 tag
                │
                └── cherry-pick / 合并回 main（若主干仍需要该修复）
```

在排查用的 worktree 里新建分支（推荐，主目录仍留在 `main`）：

```bash
cd ../investigate-0.1.0
git switch -c fix/描述性名称 v0.1.0   # 从 tag 真实新建分支并切过去
# 改代码、验证后 bump 版本发版；再视情况合回 main
```

`git switch -c <新分支> <起点>` 是正式命令，等价于 `git checkout -b <新分支> <起点>`，都会**真正创建一条分支**。

若可要求升级：在 `main` 修复并发新版本即可。

## 6. 用 worktree 按版本排查

### 6.1 它是什么

`git worktree` 是 Git **正式子命令**：同一个仓库可以挂**多个工作目录**，各自检出不同分支/tag，共用一套 `.git`。

一句话：**用某次 tag 的代码快照再挂一个目录；要真用那一版，就 `cd` 进那个目录。** 主目录不会自动变成旧版。

```text
Hiboos-ai/
├── agent-desk/              ← 主工作区，继续停在 main，照常开发
└── investigate-0.1.0/       ← 附加工作区，内容是 v0.1.0 快照（常为 detached HEAD）
```

### 6.2 和 `git checkout` 的区别

| | `git checkout v0.1.0` | `git worktree add … v0.1.0` |
|--|----------------------|------------------------------|
| 主目录文件 | **换成** 旧版 | **不变**，仍是 main |
| main 上未发布改动 | 被切走或需先 stash | 仍留在主目录 |
| 仓库里多了什么 | 一般不新增多目录 | **多一个磁盘目录**；分支/tag 列表通常不变 |
| 适用 | 整仓短暂切过去 | 排查旧版，同时本地还在 main 开发 |

启动服务、跑 CLI 时：在**哪个目录**执行，就用**哪一份**代码。

### 6.3 推荐操作（路径很重要）

在 **agent-desk 仓库根**执行，把 worktree 建到仓外：

```bash
cd /path/to/agent-desk
git fetch --tags
git worktree add ../investigate-0.1.0 v0.1.0

cd ../investigate-0.1.0
# 在此目录复现问题 / 启动服务
```

`../` 相对的是**当前所在目录**。在子目录里执行时，落点容易建进仓内，不推荐。

检出 tag 时出现 `detached HEAD` 是正常的。

### 6.4 查看与删除

```bash
git worktree list

cd /path/to/agent-desk
git worktree remove ../investigate-0.1.0
# 或使用绝对路径
```

`list` 只剩主目录一行即删除成功。

### 6.5 排查 → 修复衔接

1. 确认现场版本 → `worktree add` 对应 tag。  
2. `cd` 进排查目录复现。  
3. 需要改代码：`git switch -c fix/… <tag>`（见 §5）。  
4. 发补丁版并/或合回 `main`；用完后 `git worktree remove …`。

---

## 7. 检查清单（每次发版）

- [ ] 相关改动已在 `main` 且已 **commit**
- [ ] `package.json` 版本（及说明文档）已对齐
- [ ] 构建/发布步骤已完成
- [ ] 本地出现预期 tag（`v*` / 如有则 `v*-beta`）
- [ ] tag（及 `main`）已 **push** 到远程
- [ ] 按需验证安装或运行该版本

---

## 8. 与进行中改动共存

发版只应包含本次要上线的提交。其它进行中的功能可用独立分支或 `git stash` 暂存，发完再继续，避免混进发版 commit 与 tag 指向的树。
