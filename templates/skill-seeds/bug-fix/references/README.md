## 详解

### rules.md - 行为约束器（最高优先级）

**用途**：定义 Bug 修复过程中的核心原则和约束

**关键规则**：
1. 最小修改原则 - 只修改解决问题必须的代码
2. 不做无关修改 - 修复范围必须严格限定
3. 保持原有行为 - 不得破坏已有业务行为
4. 优先局部修复 - 先止血，再考虑优化
5. 先分析后修改 - 禁止看到报错立即改代码
6. 不猜测业务逻辑 - 业务逻辑不明确时禁止推断
7. 高风险逻辑禁止直接修改 - 需人工 Review
8. 修复必须可验证 - 必须有验证方案
9. 修复必须可回滚 - 必须考虑回滚方案
10. 修复后必须沉淀规则 - 同类问题不能重复出现

**使用方式**：任何冲突必须以 `rules.md` 为准

---

### gate-notify-template.md - 闸门京 ME 提醒（强制）

**用途**：每次开确认闸门（Bug列表 / Bug确认 / Bug原因 / 修复方案 / 建分支确认 / 提交确认 / 推送确认 / 行云部署 / 流程切换）时，对话展示闸门内容的同时，用 `jm-notify` 给当前操作用户发个人消息。

**要点**：
- 发给自己的闸门提醒无需再问「要不要发」
- 发送失败不阻塞闸门等待
- 文案含：当前节点、要做什么、可选操作、引导回对话回复

---

### bug-categories.md - Bug 场景分类标准

**用途**：提供 Bug 分类标准，辅助问题分析和修复

**分类维度**：

1. **按问题类型分类**
   - 逻辑错误
   - 数据错误
   - 配置错误
   - 并发问题
   - 性能问题
   - 依赖问题

2. **按技术层次分类**
   - 前端层
   - 接口层
   - 业务层
   - 数据层
   - 基础设施层

3. **按影响范围分类**
   - 致命
   - 严重
   - 一般
   - 轻微

**使用阶段**：
- **问题标准化阶段**：根据用户输入快速识别问题类型
- **根因分析阶段**：辅助根因分析
- **问题分级评估阶段**：辅助问题分级评估
- **修复生成阶段**：选择合适的修复模板

---

### fix-templates.md - 修复模板库

**用途**：提供常见问题的修复模板和代码示例

**模板类型**：

1. **逻辑错误修复模板**
   - 条件判断错误
   - 循环逻辑错误
   - 边界处理错误

2. **数据错误修复模板**
   - 空值处理
   - 数据格式校验
   - 数据一致性修复

3. **配置错误修复模板**
   - 配置缺失处理
   - 环境配置统一

4. **并发问题修复模板**
   - 线程安全问题
   - 死锁修复

5. **性能问题修复模板**
   - 查询优化
   - 缓存优化

6. **依赖问题修复模板**
   - 外部服务异常处理

**使用方式**：
- 根据问题类型选择对应模板
- 模板是参考，需根据实际情况调整
- 保持修复原则，调整具体实现

## 使用说明

1. **优先级**：`rules.md` > 其他参考文件
2. **适用性**：参考文件提供指导，非强制执行
3. **灵活性**：根据实际情况调整模板内容
