# Fix Implementation（修复实施）

## ⛔ 强制执行规则

**执行本阶段前，必须先读取并遵守 @references/rules.md 中的红线规则**，特别是：

1. **信息处理红线**：
   - 不允许猜测业务逻辑
   - 不允许假设用户意图、数据格式、环境配置
2. **流程执行红线**：只做本阶段定义的操作，禁止做额外的事
3. **代码修改红线**：
   - 只修改解决问题必须的代码
   - 不顺手重构、不优化、不做无关修改
   - 保持原有行为

**违反以上规则 = 流程失败**

---

## 任务

执行代码修复，解决已确认的问题。

**⚠️ 核心原则**：
- 简单问题（快速通道）：改代码前须已过闸门「Bug原因」+「修复方案」+「建分支确认」（由 SKILL.md 开）
- 复杂问题：须已过闸门「修复方案」+「建分支确认」，再按方案执行
- **未过闸门「修复方案」或「建分支确认」禁止修改任何业务代码**
- **若步骤 9 产出了 `worktree_path`：所有 Read/Edit 必须在该 worktree 下执行，禁止改主工作区**

---

## 输入

来自快速通道（简单问题）：
- 确认的问题描述
- 问题位置
- 问题根因（简单判断）

来自修复方案生成（复杂问题）：
- 修复方案（方案 A/B/C）
- 修改清单
- 测试方案
- 回滚方案
- 用户待办事项

来自创建修复分支（步骤 9，强制）：
- `fix_branch` / `worktree_path`（或用户明确跳过隔离时的当前分支）
- `feature_branch`（如有）

---

## 执行流程

### 1. 判断问题类型

**判断来源**：
- 来自快速通道 → 简单问题，直接修复
- 来自修复方案生成 → 复杂问题，按方案修复

### 2. 执行修复

#### 情况 1：简单问题（来自快速通道）

**前置条件（强制）**：进入本阶段改代码前，SKILL.md 须已依次开过：
1. **闸门「Bug原因」**（简要根因，可一句话定位 + 修复方向）
2. **闸门「修复方案」**（拟修改文件/思路摘要）
3. **闸门「建分支确认」**（feature_branch → 优先 worktree；或切到目标分支后直接改，脏区须 stash 决策）
且用户均已确认（含京 ME 提醒）。

**执行最小化修复**：
- 读取问题代码（**优先在 worktree_path**）
- 定位问题点
- 执行最小化修复
- 只修改解决问题必须的代码
- 不顺手重构、不优化

**修复原则**：
- 保持原有行为
- 只修复当前问题
- 不引入新问题
- 未过上述闸门 → **禁止改代码**

#### 情况 2：复杂问题（来自修复方案生成）

**前置条件**：闸门「修复方案」与「建分支确认」均已通过（建分支摘要已产出）。

**按已确认的方案执行**：
- 按修改清单逐项执行
- 每完成一项修改，更新任务状态

**执行步骤**：
1. 确认闸门「修复方案」+「建分支确认」已通过（未通过则**禁止改代码**，回到 SKILL.md 开闸门）
2. 若存在 `worktree_path`：后续所有文件操作以该路径为根
3. 创建任务清单跟踪修改进度
4. 按修改清单顺序执行修改
5. 每完成一个修改点，标记为已完成
6. 所有修改完成后，输出修改总结

**禁止行为**：
- ❌ 未过闸门「修复方案」/「建分支确认」就修改业务代码
- ❌ 有 worktree 却在主工作区改业务代码
- ❌ 修改方案清单之外的代码
- ❌ 顺手重构、优化
- ❌ 引入新功能

### 3. Git 状态检查

**修改前检查**（在 worktree 或用户指定工作目录中）：
```bash
# 有 worktree 时：
git -C <worktree_path> status
# 跳过隔离时：
git status
```

**检查结果处理**：
- 工作区干净 → 开始修改
- 有未提交修改 → 提示用户，是否继续
- 有 `worktree_path` 时：在 worktree 内分支须为步骤 9 的 `fix_branch`
- 跳过隔离（主仓直接改）时：当前分支须等于目标 `feature_branch`；不一致则停止，回到步骤 9 用 `ensure_checkout_branch` 处理（禁止在错误分支上改代码）

### 4. 执行代码修改

**修改操作**：
- 使用 Edit 工具修改文件（路径须落在 worktree 内，若已建分支）
- 每次修改只修改一个文件的一个位置
- 修改完成后立即验证语法正确性

**修改记录**：
- 记录每个修改点的文件路径
- 记录修改位置（行号、函数）
- 记录修改内容
- 记录修改原因

### 5. 输出修改总结

**修改完成后输出**：
```markdown
# 修复实施报告

## 问题类型
{简单问题 / 复杂问题}

## 修复方案（如适用）
{选择的方案及原因}

## 分支与工作区
- 修复分支：{fix_branch}
- worktree：{worktree_path 或 主工作区}

## 修改清单
- [x] 修改文件：{文件路径}
  - 修改位置：{行号、函数}
  - 修改内容：{具体改动}
  - 修改原因：{为什么要改}

## Git 状态
{当前 Git 状态说明}

## 下一步
进入"验证"阶段。
```

## 截止条件

### 成功
- 所有修改已完成
- 代码语法正确
- Git 状态已记录
- 修改总结已输出

### 失败
- 修改过程中发现方案不可行
- 修改引入新问题
- 用户取消修复

---

## 输出

### 修改清单
每个修改点包含：
- 文件路径
- 修改位置
- 修改内容
- 修改原因

### Git 状态
- 当前分支（应为步骤 9 的 fix_branch 或声明的当前分支）
- worktree 路径（如有）
- 修改文件列表
- 是否有未提交修改

### 修复总结
- 修复了多少个文件
- 修改了多少行代码
- 主要修改点是什么

---

## 执行要点

1. **区分问题类型**：简单问题直接修复，复杂问题按方案修复
2. **最小化修改**：只修改解决问题必须的代码，不做额外修改
3. **保持原有行为**：不改变代码的原有逻辑和行为
4. **逐项记录**：每个修改点都要记录文件、位置、内容、原因
5. **Git 状态检查**：修改前检查 Git 状态，修改后记录状态
6. **立即验证**：每次修改完成后立即验证语法正确性
7. **worktree 隔离**：有 `worktree_path` 时禁止操作主工作区

## 附录：修改原则

### 允许的修改
- ✅ 修复 Bug 必须的代码修改
- ✅ 修改方案清单中列出的修改
- ✅ 保持原有行为的最小化修改

### 禁止的修改
- ❌ 重构代码结构
- ❌ 优化代码性能
- ❌ 添加新功能
- ❌ 修改无关代码
- ❌ 改变原有行为
- ❌ 有 worktree 时仍改主工作区

### 修改范围控制
- 只修改问题相关的文件
- 只修改问题相关的函数/类
- 只修改问题相关的代码行
- 不扩大修改范围
