# CheckList Check（上线检查）

## 任务

在验证通过后、提交确认前，按需调用独立 skill **`checkList-check`**（目录：`.joycode/skills/checkList`），执行上线/发布相关检查，降低带配置与中间件变更的修复直接提交的风险。

**本阶段不改业务代码**，只执行检查并产出检查报告摘要。

---

## 输入

来自验证阶段：
- 验证结果（须已通过）
- 修改清单

来自修复实施 / git diff：
- 实际改动文件列表

可选：
- 用户指定的上线检查文档路径（HTML/MD）
- 项目内已有 `checklist.*` / `release-check.*` / `上线检查.*`

---

## 是否执行（判定）

### 必须执行

满足任一条件即执行：

1. 用户明确要求「上线检查 / 发布检查 / checklist」
2. 用户提供了检查文档路径或粘贴了清单内容
3. 本次改动涉及以下任一类型（根据修改清单 / `git diff` 判断）：
   - JMQ / MQ topic、生产者或消费者配置
   - JSF 接口消费/提供配置
   - DUCC / 配置中心项（根因排查阶段可先用 @stages/config-query.md；上线检查仍走 checkList）
   - jdos 应用配置、部署相关配置
   - 环境变量、依赖版本等上线相关变更

### 可跳过

同时满足时可跳过（须在执行日志中写明原因）：

- 纯业务代码逻辑修复（无上述配置/中间件变更）
- 未提供检查文档，且工作区也找不到清单文件
- 用户明确说「跳过上线检查」

跳过时：简要汇报「已跳过 checkList」→ 回到 SKILL.md，进入闸门「提交确认」。

---

## 执行步骤

### 步骤 1：确认检查输入

按优先级确定检查清单来源：

1. 用户本次对话提供的文件路径 / 粘贴内容
2. 仓库或工作区中的 `checklist.*`、`release-check.*`、`上线检查.*`
3. 若必须执行但缺少清单：向用户要路径或内容；用户拒绝则记录风险后进入提交确认（不伪造检查通过）

### 步骤 2：调用 `checkList-check` skill

**强制**：读取并按 `@../checkList/SKILL.md`（即 `.joycode/skills/checkList/SKILL.md`）执行完整检查流程。

要点：
- 提取 `appName`、topics 角色等全局上下文
- 能自动执行的项调用 `checkList/tools/` 下脚本
- 需人工确认的项列出待办，不强行标为通过
- 汇总通过 / 失败 / 跳过 / 待人工项

### 步骤 3：输出摘要并回传 SKILL

```markdown
## 上线检查摘要（checkList）

- 是否执行：是 / 跳过（原因：…）
- 清单来源：{路径或「用户粘贴」}
- 结果：通过 / 有失败 / 有待人工项
- 失败项：{列表或无}
- 待人工项：{列表或无}
- 详细报告：{如有落盘路径}
```

---

## 截止条件

### 成功（可进入提交确认）

- 已执行检查且**无阻塞性失败**；或
- 已按规则合法跳过；或
- 有失败/待人工项，但用户已知晓并仍要求继续（须在闸门「提交确认」中再次体现风险）

### 失败（不建议直接提交）

- 检查存在阻塞性失败，且用户未明确接受风险继续
- **处理**：汇报失败项 → 回到 SKILL.md；默认不开「提交确认」推进 commit，除非用户明确「仍要提交」

---

## 输出

- 上线检查摘要（必有）
- 是否跳过及原因（如跳过）
- 失败项 / 待人工项列表（如有）
- 供闸门「提交确认」展示的风险提示（如有）

---

## 与闸门的关系

- 本阶段**本身不是确认闸门**
- 完成后由 SKILL.md 开 **闸门「提交确认」**（含京 ME）
- 若检查有失败或待人工项，提交确认文案中**必须摘要风险**，再问是否仍要 git commit

---

## ⛔ 重要提示

- ❌ 禁止在本阶段修改业务代码
- ❌ 禁止未读 `checkList/SKILL.md` 就假装已检查
- ❌ 禁止把「跳过」写成「检查通过」
- ❌ 禁止检查失败却静默进入 commit
- ✅ 执行完必须回到 SKILL.md 决定下一步
