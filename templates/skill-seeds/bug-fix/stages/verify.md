# Verification（验证）

> 验证纪律（证据要求、禁语清单、失败处理）见 `skills/verification-before-completion/SKILL.md`：无验证证据不得宣布修好。

## ⛔ 强制执行规则

**执行本阶段前，必须先读取并遵守 @references/rules.md 中的红线规则**，特别是：

1. **信息处理红线**：
   - 不允许猜测业务逻辑
   - 不允许假设用户意图、数据格式、环境配置
2. **流程执行红线**：只做本阶段定义的操作，禁止做额外的事
3. **验证红线**：
   - 必须提供可验证的证据
   - 不能通过说"已验证"来宣布完成
   - 验证失败必须明确说明问题

**违反以上规则 = 流程失败**

---

## 任务

验证修复是否有效，提供可检查的证据。

**核心目标**：回答三个问题
1. 问题是否解决？
2. 是否引入新问题？
3. 证据是什么？

---

## 输入

来自修复实施阶段（fix-implementation）的输出：
- **修改清单**：具体修改了哪些文件和代码
- **修改原因**：为什么要这样修改
- **Git 状态**：当前代码状态

来自修复方案生成（如适用）：
- **修复方案**：修复策略和预期效果
- **测试方案**：如何验证修复

---

## 执行流程

### 1. 前置检查

**目的**：确认输入完整性

**操作步骤**：
1. 检查是否存在修改清单
   - 使用 `git status` 查看当前修改
   - 使用 `git diff` 查看修改内容
2. 如果修改清单为空：
   - 输出"无代码修改，跳过验证阶段"
   - 直接进入下一阶段（治理沉淀）

**输出**：
```markdown
## 前置检查结果
- 修改文件数：{数量}
- 修改内容：{简要描述}
- 检查结论：{通过/无修改}
```

---

### 2. 审查修改代码（静态验证）

**目的**：检查修改后的代码质量

**操作步骤**：

#### 2.1 读取修改文件
- 使用 Read 工具读取修改清单中的所有文件
- 重点关注修改位置附近的代码

#### 2.2 执行代码审查检查项
逐项检查以下内容：

**检查项清单**：
- [ ] **语法正确性**：代码能否编译/解释（检查语法错误、拼写错误）
- [ ] **逻辑完整性**：修改逻辑是否覆盖所有分支（if/else、异常处理）
- [ ] **边界处理**：是否处理了边界情况（空值、极端值、特殊条件）
- [ ] **异常处理**：是否捕获并正确处理可能的异常
- [ ] **命名规范**：变量/函数命名是否清晰（符合项目规范）
- [ ] **注释清晰**：关键逻辑是否有必要的注释

#### 2.3 记录审查结论

**输出格式**：
```markdown
## 代码审查结果

### 审查范围
- 文件：{文件路径列表}
- 函数：{修改的函数名列表}

### 审查检查项
- [x] 语法正确性：{结论}
- [x] 逻辑完整性：{结论}
- [x] 边界处理：{结论}
- [x] 异常处理：{结论}
- [x] 命名规范：{结论}
- [x] 注释清晰：{结论}

### 发现问题
{如果有问题，列出问题清单；如果没有，写"无"}

### 改进建议
{如果有建议，列出建议清单；如果没有，写"无"}

### 审查结论
- 结果：{通过/发现问题}
- 问题严重性：{严重/一般/轻微}（如果有问题）
```

**发现问题时的处理**：

**严重问题**（必须修复）：
- 语法错误导致无法编译
- 逻辑错误导致功能异常
- 遗漏关键的边界处理

**处理方式**：
- 输出代码审查结果
- **进入失败流程**（回滚 → 复盘 → 回到问题定位）

**一般问题**（建议修复）：
- 命名不够清晰
- 注释不完整
- 代码风格问题

**处理方式**：
- 记录问题
- **继续验证**（在验证报告中记录问题）

---

### 3. 验证问题解决（动态验证）

**目的**：证明修复有效

**验证方式优先级**：
1. **自动化测试**（优先）：通过测试用例验证
2. **配置生效验证**（配置类修复必做）：见下方 3.0
3. **代码逻辑验证**（备选）：通过逻辑推演验证
4. **用户验证清单**（最后）：由用户手动验证

#### 3.0 配置变更验证（按需，强制）

若本次修复涉及 DUCC / 配置中心项变更，或根因分析结论为「配置驱动」：

1. 按 @stages/config-query.md 再次查询相关配置项
2. 确认 `isReleased=true` 且 `value` 与修复方案一致
3. 将查询 JSON / 关键字段写入验证报告作为证据

未涉及配置变更则跳过本小节。

#### 优先级 1：执行或编写测试用例

**目的**：通过自动化测试验证修复有效性

**操作步骤**：

##### 1. 查找相关测试文件

**提取问题关键词**：
- 从问题描述中提取核心名词（如：订单、用户、支付）
- 从修改文件名中提取类名或模块名（如：OrderService、UserManager）

**查找测试文件**：
```bash
# Java 项目：查找相关测试文件
find . -name "*Test.java" -o -name "*Tests.java" | grep -i "{关键词}"

# Node.js 项目：查找测试文件
find . -name "*.test.js" -o -name "*.spec.js" | grep -i "{关键词}"

# Go 项目：查找测试文件
find . -name "*_test.go" | grep -i "{关键词}"
```

**示例**：
- 问题：订单查询空指针异常
- 关键词：`order`、`OrderService`
- 查找命令：`find . -name "*Test.java" | grep -i "order"`

##### 2. 判断测试情况

**情况 A：已有相关测试用例**
- 执行测试：`mvn test -Dtest={测试类}` / `npm test` / `go test ./...`
- 记录测试结果
- 测试通过 → 验证通过，继续下一步
- 测试失败 → 分析失败原因（见下方"测试失败分析"）

**情况 B：无相关测试用例**
- 编写最小化测试用例验证修复
- 执行测试
- 测试通过 → 验证通过，继续下一步
- 测试失败 → 分析失败原因（见下方"测试失败分析"）

**测试失败分析**：

**判断标准**：
1. **检查测试用例是否正确**：
   - 测试数据是否准确反映问题场景
   - 断言是否正确
   - 测试逻辑是否合理

2. **检查代码修改是否正确**：
   - 修改是否真的解决了问题
   - 是否遗漏了其他场景
   - 是否引入了新问题

**判断方法**：
- **代码问题**：测试逻辑正确，但代码修改未能解决问题
- **测试问题**：代码修改合理，但测试用例编写错误（数据错误、断言错误）
- **理解问题**：测试和代码都"正确"，但问题依然存在（说明根因定位错误）

**处理方式**：
- 代码问题 → 进入失败流程（回滚 → 复盘 → 回到根因分析）
- 测试问题 → 修正测试用例，重新验证
- 理解问题 → 进入失败流程（回滚 → 复盘 → 回到问题标准化）

##### 3. 编写最小化测试用例（如需要）

**测试用例要求**：
- **最小化原则**：只验证当前修复的问题场景
- **覆盖问题场景**：测试用例必须覆盖问题描述中的场景
- **可执行性**：测试用例必须能够独立执行
- **清晰命名**：测试方法名清晰说明测试意图

**测试用例内容**：
```java
// Java 示例
@Test
public void testFix_{问题描述}() {
    // Given: 准备问题场景的数据
    {准备触发问题的数据/条件}
    
    // When: 执行修复后的代码
    {调用修复后的方法}
    
    // Then: 验证问题已解决
    {断言预期结果}
}
```

```javascript
// JavaScript 示例
test('fix: {问题描述}', () => {
    // Given: 准备问题场景的数据
    {准备触发问题的数据/条件}
    
    // When: 执行修复后的代码
    {调用修复后的方法}
    
    // Then: 验证问题已解决
    expect({实际结果}).toBe({预期结果});
});
```

**测试用例位置**：
- Java: `src/test/java/{包路径}/{类名}Test.java`
- Node.js: `__tests__/{模块名}.test.js` 或 `src/{模块名}.test.js`
- Go: `{源文件}_test.go`

##### 4. 执行测试并记录结果

**执行测试**：
```bash
# Java
mvn test -Dtest={测试类名}

# Node.js
npm test {测试文件}

# Go
go test -v {测试文件}
```

**记录测试结果**：
```markdown
## 测试验证结果

### 测试情况
- 测试类型：{已有测试/新增测试}
- 测试文件：{文件路径}
- 测试方法：{方法名}

### 测试执行
- 执行命令：{具体命令}
- 测试结果：{通过/失败}

### 测试证据
{测试输出日志，包括通过/失败的断言}

### 验证结论
- 问题是否解决：{是/否}
- 判断依据：{测试结果}
```

**⚠️ 重要提示**：
- 只编写**验证当前修复**的测试用例
- **不补充完整测试套件**（不是补充边界测试、异常测试等）
- 测试用例失败时，分析是代码问题还是测试问题

#### 优先级 2：代码逻辑验证（如果无法执行测试）

**分析修复逻辑**：
1. 阅读修改前的代码（使用 `git diff`）
2. 阅读修改后的代码（使用 Read 工具）
3. 分析修改如何解决问题：
   - 修改前：{原有逻辑}
   - 修改后：{新逻辑}
   - 为什么能解决问题：{逻辑推演}

**验证修复有效性**：
- 问题场景：{什么情况下会触发问题}
- 修复逻辑：{修改后的代码如何处理这个场景}
- 预期结果：{修复后应该得到什么结果}

#### 优先级 3：用户验证清单（如果 AI 无法验证）

**生成用户验证清单**：
```markdown
## 用户验证清单

### 验证准备
1. 环境准备：{需要准备的环境}
2. 数据准备：{需要准备的测试数据}

### 验证步骤
1. {具体验证步骤 1}
2. {具体验证步骤 2}
3. {具体验证步骤 3}

### 预期结果
- {预期看到的结果 1}
- {预期看到的结果 2}

### 注意事项
- {需要特别注意的点}
```

**输出格式**：
```markdown
## 问题解决验证

### 验证方式
{自动化测试/代码逻辑验证/用户验证清单}

### 验证过程
{具体执行了什么操作}

### 验证证据
{测试结果/逻辑推演/验证清单}

### 验证结论
- 问题是否解决：{是/否/待用户验证}
- 判断依据：{为什么判断解决/未解决}
```

### 4. 确认影响范围（回归验证）

**目的**：确认实际修改的影响范围与预期一致，检查是否引入新风险

**核心原则**：
- 根因分析阶段已评估过影响范围
- 修复方案生成阶段已评估过风险
- 验证阶段是"确认符合预期"，发现偏差时输出问题和建议

**操作步骤**：

#### 4.1 获取预期影响范围

**来源**：
- 从根因分析报告中获取：影响范围（代码范围、功能范围）
- 从修复方案报告中获取：方案的影响范围、风险评估

**记录预期**：
```markdown
## 预期影响范围（来自前面阶段）

### 根因分析阶段的影响范围
- 代码范围：{哪些代码文件}
- 功能范围：{哪些业务功能}

### 修复方案阶段的风险评估
- 方案影响：{方案的影响范围}
- 风险评估：{方案的风险点}
```

#### 4.2 分析实际影响范围

**使用 Grep 工具搜索调用方**：
```bash
# 搜索函数调用
grep -r "functionName" --include="*.java" .

# 搜索类引用
grep -r "ClassName" --include="*.java" .
```

**记录实际**：
```markdown
## 实际影响范围（验证阶段分析）

- 调用方数量：{数量}
- 调用方文件：{文件列表}
```

#### 4.3 对比预期与实际

**对比分析**：
```markdown
## 影响范围对比

| 维度 | 预期（前面阶段） | 实际（验证阶段） | 是否一致 |
|------|----------------|----------------|---------|
| 代码文件 | {文件列表} | {文件列表} | {是/否} |
| 调用方数量 | {数量或描述} | {数量} | {是/否} |
```

#### 4.4 检查副作用

**检查项**：
- [ ] **功能影响**：是否影响其他功能的正常工作
- [ ] **性能影响**：是否影响系统性能
- [ ] **兼容性影响**：是否破坏向后兼容性
- [ ] **数据影响**：是否影响数据处理逻辑

#### 4.5 分析风险来源

**发现风险时，必须判断来源**：

**风险来源判断方法**：

1. **检查是否本次修改引入**：
   - 使用 `git diff` 查看修改内容
   - 分析风险点是否与修改直接相关
   - 检查修改前是否存在该问题

2. **判断标准**：
   - **以前就存在**：风险点与本次修改无关，是历史遗留问题
   - **本次修改引入**：风险点由本次修改直接导致

3. **验证方法**：
   ```bash
   # 回滚代码，检查风险是否消失
   git stash
   {检查风险是否存在}
   git stash pop
   ```

**处理方式**：

**情况 A：风险以前就存在**
- **输出**：风险描述、历史原因
- **建议**：与用户确认是否需要修复历史问题
- **后续**：不影响本次修复验证结果

**情况 B：风险由本次修改引入**
- **输出**：风险描述、引入原因、修改点
- **建议**：方案设计有遗漏，需要重新评估
- **后续**：输出问题，由 SKILL.md 决定流程跳转

**输出格式**：
```markdown
## 回归检查结果

### 影响范围对比
- 预期影响：{来自根因分析和修复方案}
- 实际影响：{验证阶段的分析}
- 对比结论：{符合预期/发现偏差}

### 副作用检查
- [x] 功能影响：{结论}
- [x] 性能影响：{结论}
- [x] 兼容性影响：{结论}
- [x] 数据影响：{结论}

### 风险分析（如发现风险）
- 风险描述：{具体风险}
- 风险来源：{以前就存在/本次修改引入}
- 引入原因：{如果是本次引入，说明哪个修改点引入}
- 历史原因：{如果是以前存在，说明历史原因}

### 风险处理建议
{根据风险来源给出建议}
- 以前就存在：与用户确认是否需要修复
- 本次引入：建议重新评估修复方案

### 回归检查结论
- 结果：{通过/发现问题}
- 问题类型：{历史问题/方案问题}
- 严重程度：{高/中/低}
```

## 截止条件

### 成功
- 前置检查完成
- 代码审查完成
- 问题验证完成（测试通过 或 逻辑验证通过 或 用户验证清单已提供）
- 回归检查完成
- 验证报告已输出

### 失败 → 输出问题和建议

**验证失败场景**：
1. 代码审查发现严重问题
2. 测试验证失败（代码问题或理解问题）
3. 回归检查发现方案问题（风险由本次修改引入）

**失败处理原则**：
- **本阶段只输出问题和建议**
- **不决定跳转到哪个阶段**（由 SKILL.md 决定）
- **输出完整的问题信息**，供 SKILL.md 做决策

**输出格式**：
```markdown
## 验证失败报告
```

3. **验证方式明确**：优先自动化测试（可编写测试），其次逻辑验证，最后用户验证
