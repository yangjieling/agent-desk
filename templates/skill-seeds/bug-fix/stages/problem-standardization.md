# Problem Standardization（问题标准化）

## ⛔ 强制执行规则

**执行本阶段前，必须先读取并遵守 @references/rules.md 中的红线规则**，特别是：

1. **信息处理红线**：
   - 不允许猜测业务逻辑（业务规则不明确时必须询问）
   - 不允许假设用户意图、数据格式、环境配置
2. **流程执行红线**：只做本阶段定义的操作，禁止做额外的事

**违反以上规则 = 流程失败**

---

## 任务

将用户的零散输入转换为清晰、结构化的问题描述，为后续分析提供坚实基础。

---

## 输入

来自输入识别或问题分级的信息：
- 输入类型
- **Bug 类型**（code-error / logic-deviation）
- 异常详情（如有）
- 问题现象（如有）
- 日志内容（如有）

---

## 执行步骤

### 步骤 1：提取问题位置

从输入中识别：
- 问题所在模块
- 问题所在页面或接口
- 技术层次（前端/接口/业务层/数据层）

### 步骤 2：明确行为对比

识别并记录：
- 期望行为：应该发生什么
- 实际行为：实际发生了什么
- 行为差异：两者之间的差距

### 步骤 3：整理异常信息

如有异常，提取：
- 异常类型
- 异常消息
- 堆栈信息
- 出错位置（文件、行号）

### 步骤 4：识别复现条件

尽可能明确：
- 触发条件
- 复现步骤
- 环境信息
- 发生频率（必现/偶现）

### 步骤 5：补全缺失信息

如果关键信息缺失：
- 向用户精确提问
- **提问要求**：
  - 必须具有专业性：使用技术术语，避免模糊表述
  - 必须具有针对性：聚焦缺失的关键信息，不发散
  - 给出选项而非开放式问题
- **追问策略**：持续追问直到问题清晰，信息完整

---

## 截止条件

### 成功（继续流程）
- 问题位置已明确
- 期望行为和实际行为已明确
- 关键信息完整度 ≥ 80%
- Bug 类型已确认（code-error 或 logic-deviation → code-error）

**确认闸门（由 SKILL.md 开）**：本阶段成功产出后，必须经 **闸门「Bug确认」**（含京 ME）用户确认后，方可进入上下文分析 / 根因。

### 失败（终止流程）
- 用户拒绝提供关键信息：
  - **处理方式**：告知用户"对不起，缺少关键信息无法准确定位问题，流程终止"
  - 建议用户准备好信息后重新开始
- 信息严重不足且无法补充：
  - **处理方式**：输出已收集的信息，建议用户补充后重新开始
- 确认为需求变更（logic-deviation 类型判断为类型 2）：
  - **处理方式**：输出流程终止报告，推荐使用需求开发流程
  - **不继续后续阶段**

---

## 输出

### Bug 类型
- **类型**：code-error（代码错误）
- **说明**：logic-deviation 已在本阶段处理完毕

### 问题位置
- 模块：问题所在的业务模块
- 页面/接口：具体的页面或接口
- 技术层次：前端/接口/业务层/数据层

### 行为对比
- 期望行为：应该发生什么
- 实际行为：实际发生了什么

### 异常信息（如有）
- 异常类型：如 NullPointerException
- 异常消息：具体的错误信息
- 堆栈信息：完整的调用链
- 出错位置：文件名和行号

### 复现条件
- 触发条件：什么情况下会出现
- 复现步骤：如何重现问题
- 环境信息：测试/生产等
- 发生频率：必现/偶现

### 其他信息
- 日志片段：相关的日志内容
- 用户补充：用户提供的额外信息

## 附录：logic-deviation 类型处理

当 Bug 类型为 `logic-deviation`（需求偏差）时，问题标准化需按需增加以下步骤。

### 触发条件

以下情况需要加载需求上下文：
- 用户明确提到需求不一致、预期不符
- 现象描述包含"应该是"、"需求要求"、"PRD 规定"等关键词
- 需要对照需求文档才能准确定位问题

### 补充步骤：需求上下文加载

1. **检测关联需求**：
   ```bash
   # 检测 .harness/changes/ 下是否有相关需求目录
   CHANGE_DIR=$(ls -d .harness/changes/*/ 2>/dev/null | sort -r | head -1)
   [ -n "$CHANGE_DIR" ] && {
     [ -f "${CHANGE_DIR}spec.html" ] && echo "SPEC_EXISTS"
     [ -f "${CHANGE_DIR}design.html" ] && echo "DESIGN_EXISTS"
   }
   ```

2. **加载需求文档**（如存在）：
   - 加载 `spec.html` → 提取相关验收标准
   - 加载 `design.html` → 提取设计意图

3. **明确偏差**：
   - 预期行为：{需求/设计要求的}
   - 实际行为：{用户描述的}
   - 偏差点：{两者差异}

### ⚠️ 无法加载需求时的处理

**触发条件**：需求文档不存在或无法找到相关需求

**必须让用户明确判断类型**：

```markdown
## 需求偏差类型判断

检测到您报告的问题属于"需求偏差"类型，但未找到相关需求文档。

**问题描述**：{用户描述的问题}

**请判断问题类型**：

### 类型 1：需求未实现（代码异常）
- **特征**：需求文档中有明确要求，但代码没有实现
- **示例**：需求要求"订单状态变更时发送通知"，但代码中没有发送通知的逻辑
- **处理方式**：退回 code-error 类型，按代码异常修复
- **流程**：继续 Bug 修复流程

### 类型 2：需求变更
- **特征**：需求文档中没有此功能要求，是新提出的变更
- **示例**：需求中没有"订单取消后恢复库存"，现在要求增加此功能
- **处理方式**：停止 Bug 修复流程，推荐使用需求开发流程
- **流程**：终止当前流程，引导用户使用需求开发流程

---

**请回复**：
- 回复"1" → 类型 1：需求未实现，按代码异常修复
- 回复"2" → 类型 2：需求变更，使用需求开发流程
- 回复"取消" → 终止流程

**⚠️ 提示**：如果不确定，建议先查找需求文档或与产品确认。
```

**禁止行为**：
- ❌ 不询问用户直接修复（可能导致修错方向）
- ❌ 问模糊问题（如"你觉得呢？"、"怎么办？"）
- ❌ 提供超过 2 个选项（避免选择困难）

**提问原则**：
- ✅ 必须提供明确的选择项（类型 1 / 类型 2）
- ✅ 每个类型说明特征、示例、处理方式、流程
- ✅ 聚焦核心问题：是需求未实现还是需求变更

### 类型判断后的处理

#### 类型 1：需求未实现（退回 code-error）

**修改 Bug 类型**：
```markdown
**Bug 类型更新**：logic-deviation → code-error

**原因**：需求文档中有明确要求，但代码没有实现，属于代码异常。

**继续流程**：按 code-error 类型继续问题标准化流程。
```

**不再输出需求上下文**，因为已经确认是代码异常。

#### 类型 2：需求变更（终止流程）

**输出流程终止报告**：

```markdown
# 流程终止报告

## 问题类型
**类型**：需求变更

**说明**：该问题属于新功能需求，而非 Bug。需求文档中没有此功能要求，建议使用需求开发流程。

## 建议
推荐使用需求开发流程：
1. **需求分析**：使用 `request-analysis` Skill
2. **技术设计**：使用 `tech-design` Skill
3. **任务拆分**：使用 `task-breakdown` Skill
4. **编码实现**：使用 `coding-impl` Skill

## 下一步
请重新启动需求开发流程，或与产品确认需求详情。

**流程终止**。
```

**终止当前流程**，不生成待办清单文档。
