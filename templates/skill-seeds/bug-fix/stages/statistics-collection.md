# Statistics Collection（统计收集与上报）

## 地位

**Bug-Fix 流程的最后一环**，每个问题解决后必须执行。

---

## 🔴 强制要求

- **每个问题解决后都必须上报一次**
- 不执行统计收集，流程不完整
- 用户取消流程后无法继续执行，不上报

---

## 任务

收集本次 Bug 修复的统计数据并上报，生成最终汇报，完成流程闭环。

**核心目标**：
1. 统计交互数据
2. 生成最终汇报
3. 调用脚本上报
4. 推送问题记录
5. 推荐代码审查

---

## 输入

来自执行日志：
- **执行记录**：每个步骤的执行情况
- **错误记录**：过程中发现的问题
- **经验教训**：治理沉淀阶段提取的经验教训

来自治理沉淀阶段：
- **修复报告**：完整的修复过程记录
- **预防规则**：提炼的预防措施
- **检查项**：沉淀的检查清单

---

## 执行步骤（必须按顺序执行）

### 步骤 1：读取执行日志

**目的**：获取完整的执行记录

**操作**：
1. 读取执行日志文件：`.harness/wiki/bug-fix/execution-log-{YYYYMMDD}-{HHmm}.md`
2. 提取以下信息：
   - 基本信息（问题简述、流程类型、问题类型）
   - 执行步骤记录（总耗时、执行步骤数、回退次数、错误次数）
   - 错误记录
   - 经验教训

---

### 步骤 2：总结用户问题

**执行**：
1. 分析用户描述的问题
2. 提取问题类型、涉及模块、具体表现
3. 用专业语言总结成简洁表述

**格式要求**：
- 长度：10-50 字符（最小 5 字符）
- 结构：`{问题类型}：{涉及模块/功能} {具体表现}`
- 专业、简洁、准确

**输出**：
```
用户问题总结：
"{问题类型}：{涉及模块/功能} {具体表现}"
```

**示例**：
```
用户问题总结：
"并发问题：海博田支付回调与超时消息并发导致数据不一致"
```

---

### 步骤 3：统计交互次数

**执行**：
1. **识别问题边界**：
   - 问题开始：用户首次提出问题（如"海博田回调并发问题"、"有个空指针异常"）
   - 问题结束：用户确认问题已解决（如"可以了"、"没问题了"、"提交吧"、"确认"）

2. **统计问题区间内的交互**：
   - 遍历问题开始到问题结束之间的对话
   - **问答轮次**：统计用户的**所有输入次数**（提问、回复、确认、补充信息等）
   - **打断次数**：统计用户打断 AI 的次数（标记："不对"、"重新分析"、"换个思路"、"不是这样"、"理解错了"）

3. **排除问题区间外的对话**：
   - 问题结束后的对话不计入
   - 新问题的对话不计入

**输出**：
```
问题边界：
- 问题开始：{用户首次提出问题的内容}
- 问题结束：{用户确认问题已解决的内容}

交互统计（仅统计问题区间内）：
- 问答轮次：{数字} 次（用户输入总次数）
  明细：
  1. {用户输入内容简述}
  2. {用户输入内容简述}
- 打断次数：{数字} 次
  明细：
  1. {打断位置简述}
```

---

### 步骤 4：扫描历史记录

**执行**：
```bash
find .harness/wiki/bug-fix -name "report-*.md" -mtime -7
```

**输出**：
```
历史记录扫描：
- 近7天报告数：{数字}
- 问题反复：是/否
- 问题位置：是/否
```

---

### 步骤 5：输出统计数据清单

**⛔ 强制输出**：

```markdown
## 统计数据清单

### 1. 用户问题总结
"{问题类型}：{涉及模块/功能} {具体表现}"

### 2. 问题边界
- 问题开始：{用户首次提出问题的内容}
- 问题结束：{用户确认问题已解决的内容}

### 3. 交互统计（仅统计问题区间内）
- 问答轮次：{数字} 次（用户输入总次数）
  明细：{简要列出用户输入内容}
- 打断次数：{数字} 次
  明细：{简要列出打断位置}

### 4. 历史记录
- 问题反复：是/否
- 问题位置：是/否

---

## 闸门「服务评价」

**请对本次服务进行评价**

## oh-choices
- 好 | 好
- 还可以 | 还可以
- 差 | 差
```

**说明**：
- 输出统计数据清单，让用户了解统计结果
- **必须开闸门「服务评价」**，输出 `## oh-choices` 后**立即停止**，等待用户点击「好 / 还可以 / 差」
- ❌ 禁止把「好 / 还可以 / 差」只写在同一行正文里而不出选项块
- ❌ 禁止输出评价问句后在同一轮继续上报（不回复就默认「还可以」只适用于用户已看到选项却回复了其它内容）
- 不需要用户确认统计数据是否正确；数据以已收集到的为准

---

### 步骤 6：收集用户评价

**任务**：收集用户评价（闸门「服务评价」，必须等用户回复）

**处理规则**：
- 用户回复"好"/"还可以"/"差" → 记录评价，继续步骤 8
- 用户回复其他内容 → 使用默认值"还可以"，继续步骤 8

**注意**：
- 不需要等待用户确认统计数据
- 数据以已收集到的为准
- 用户评价是唯一的交互确认点；**未收到回复前禁止调用上报脚本**

---

### 步骤 7：统计代码修改

**目的**：为执行日志生成最终汇报（由 SKILL.md 统一管理）

**操作**：
准备最终汇报数据，供 SKILL.md 写入执行日志：

```markdown
## 最终汇报

### 执行统计
- 总耗时：{分钟}
- 执行步骤数：{数量}
- 回退次数：{数量}
- 错误次数：{数量}

### 问题记录（推送）
本次出现问题：
1. {错误描述}，原因是 {原因}
2. {错误描述}，原因是 {原因}

### 经验教训
- {经验教训 1}
- {经验教训 2}

### 用户评价
- 评价：{好/还可以/差}
```

---

### 步骤 8：调用脚本上报

**使用正确的格式调用脚本**：

```bash
bash ~/.harness/scripts/report-bug-issue.sh \
  --title "问题标题" \
  --question-summary "用户问题" \
  --rounds {数字} \
  --interruptions {数字} \
  --user-rating "好|还可以|差" \
  --is-recurring "是|否" \
  --same-location "是|否" \
  --doc
```

**参数说明**：
- `--title`：问题标题（10-100 字符）
- `--question-summary`：用户问题（5-100 字符）
- `--rounds`：问答轮次（0-50 的整数）
- `--interruptions`：打断次数（0-10 的整数）
- `--user-rating`：用户评价（只能是：好/还可以/差）
- `--is-recurring`：问题反复（只能是：是/否）
- `--same-location`：问题位置（只能是：是/否）
- `--doc`：生成文档标志

**注意**：去掉了 `--self-score` 和 `--self-evaluation` 参数。

---

## 输出文件

### 必须输出
- **统计报告**：通过脚本上报到 JoySpace
- **问题记录推送**：追加到 `.harness/wiki/bug-fix/issues.md`（在治理沉淀阶段已完成）
- **最终汇报数据**：供 SKILL.md 写入执行日志

### 可选输出
- **本地日志**：`~/.harness/logs/bug-issue.log`（脚本自动生成）

## ⛔ 重要提示

**统计收集完成后，Bug-Fix 流程结束**

**流程结束后的建议**：
- 建议用户使用 `code-review` skill 对修改的代码进行独立审查
- 说明：代码审查不在 bug-fix 流程内，是独立的质量保障环节

**禁止行为**：
- ❌ 跳过用户评价环节
- ❌ 不调用上报脚本
- ❌ 在流程结束后继续执行其他步骤

## 字段收集规范

### AI 必填字段（6个）

| 字段 | 类型 | 格式要求 | 来源 |
|-----|------|---------|------|
| question-summary | string | 10-50 字符，结构：`{问题类型}：{涉及模块/功能} {具体表现}` | 用户描述总结 |
| rounds | integer | 0-50 的整数 | 统计问题区间内用户输入次数 |
| interruptions | integer | 0-10 的整数 | 统计问题区间内用户打断次数 |
| user-rating | string | 只能是：好/还可以/差 | 询问用户 |
| is-recurring | string | 只能是：是/否 | 扫描近7天历史报告 |
| same-location | string | 只能是：是/否 | 对比修改位置 |

### 脚本自动获取字段（7个）

| 字段 | 获取方式 |
|-----|---------|
| ERP | `git config user.name` |
| 时间 | `date +"%Y-%m-%d %H:%M:%S"` |
| 仓库 | `git remote get-url origin` |
| 代码行数 | `git diff --shortstat` |
| 文件数 | `git diff --name-only` |
| 会话id | 环境变量 `$JOYCODE_SESSION_ID` |
| 问题标题 | AI 提供（--title） |
| 问题描述 | AI 提供（--desc，可选） |
| 修复结果 | AI 提供（--result，可选） |

### 仅统计不上报字段（1个）

| 字段 | 获取方式 | 说明 |
|-----|---------|------|
| 修改简介 | `git diff --numstat` | 仅记录到执行日志，不上报 |

## 用户反馈处理

| 用户反馈 | AI 行为 |
|---------|--------|
| "好"/"还可以"/"差" | 记录评价，继续上报 |
| 其他内容 | 使用默认值"还可以"，继续上报 |
| 明确拒绝上报 | 记录"用户拒绝"，不调用上报脚本 |

---

## 执行要点

1. **必须读取执行日志**：执行日志是本阶段的核心输入
2. **客观统计**：问答轮次和打断次数必须准确统计
3. **用户评价**：必须开闸门「服务评价」+ `## oh-choices`，等用户点选后再上报
4. **流程闭环**：本步骤完成后，Bug-Fix 流程结束
5. **推荐代码审查**：流程结束后，推荐使用 code-review skill
