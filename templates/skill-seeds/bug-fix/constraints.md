# BugFix 约束规则

本文档定义 Bug 修复流程中必须遵守的所有约束，优先级仅次于 `references/rules.md`。

---

## 一、交互约束

### 1.1 逐步汇报 + 确认闸门

**逐步汇报（非闸门）**
- 每完成一步，用 1～3 句话简要汇报本步结论与下一步动作
- 非确认闸门步骤**自动推进**，不等待用户回复
- 禁止在未过闸门时连续改代码 / 提交 / 切换类型

汇报格式：
```
📍 Step N 完成：{一句话结论}
→ 下一步：{即将做什么}
```

**确认闸门（必须等用户回复）**

| 闸门 | 时机 | 确认内容 | 未确认前禁止 |
|------|------|----------|--------------|
| **Bug列表** | 锁定目标 Bug（列表选定 / 单条复述） | 要处理哪条 Bug | 进入详情对齐 / 排查 |
| **Bug确认** | 问题标准化完成，或快速通道问题确认完成 | 现象、复现、预期理解无误 | 深入根因 / 改代码 |
| **Bug原因** | 根因分析完成（完整流程）；快速通道在改代码前给出简要根因 | 根因结论正确 | 提出详细修复方案或改代码 |
| **修复方案** | 修复方案生成后；快速通道在改代码前给出拟修复摘要 | 方案可接受 | 修改任何业务代码 |
| **建分支确认** | 修复方案通过后、改代码前 | feature_branch（优先【分支名称】）；是否 worktree；脏区是否 stash 切换 | 未确认前禁止建分支 / 改业务代码；「直接改」须已在目标分支 |
| **提交确认** | 验证通过且上线检查完成（或合法跳过）后 | 同意提交 | git commit |
| **推送确认** | git commit 成功后 | 是否推送到远程（可跳过） | 未确认前禁止 pull/push |
| **行云部署** | **push 成功** 后 | 是否部署到行云（可跳过） | 未确认前禁止触发构建/部署 |
| **流程切换** | Bug 类型或流程路径切换时 | 同意切换并调整策略 | 按新类型/新路径继续 |
| **服务评价** | 统计收集完成、上报脚本前 | 好 / 还可以 / 差 | 未回复前禁止上报 |

闸门回复约定：
- 「确认 / 同意 / 可以 / OK / 继续」→ 进入下一步
- 提出修正 → 更新后**再次走同一闸门**
- 「换一个 / 先不修 / 暂停」→ 停止或回到闸门「Bug列表」

**目的**：关键决策由用户把关；其余步骤只汇报不阻塞。

### 1.1.0 hb Web 快捷选项块（hb 任务，能用选项时输出）

任务经 **hb Web / 流程编排** 执行时，开确认闸门且仍在等待用户回复：

- **固定选项即可闭环**（确认 / 取消 / 选序号等）→ 在「回复方式」之前追加 `## hb-choices`
- **需要用户自由输入文本**（补字段、描述修正、自定义分支名等）→ **不要**输出选项块，说明需输入什么，让用户在输入框手动回复

```markdown
## hb-choices
- 按钮展示文案 | 用户点击后发送的回复
- …
```

| 规则 | 说明 |
|------|------|
| 何时输出 | 仅当本轮可用固定选项表达；需手动输入时不输出 |
| 格式 | 每行 `- 展示文案 \| 回复值`；回复值须可被 Agent 单独理解 |
| 语义 | 展示文案写清本轮选项（含缺陷编号/分支号等），勿只写「确认」 |
| 数量 | 2～6 条，仅列本轮真实可选操作 |
| 收口 | 闸门已确认/已结束时**禁止**输出 `## hb-choices` |
| 一致 | 若另有「选项：」列表，须与 `## hb-choices` 一致 |

hb 会据此渲染日志窗口可点击按钮；未输出且无固定选项时，用户直接在输入框回复即可。

### 1.1.1 闸门京 ME 消息提醒（强制）

开上述任一确认闸门时，**除在对话中展示确认内容并等待回复外**，必须同步给当前操作用户发京 ME 个人消息提醒（用户可能不在对话页）。

| 项 | 约定 |
|----|------|
| 收件人 | 当前操作用户 ERP（`OPT_ERP` > `ERP` > `USER` > `jm-notify` 默认 erp；未知则短问一次） |
| 时机 | 每次打开确认闸门（含同闸门再次确认）时，与对话闸门展示同步发送 |
| 是否再确认 | 发给自己的闸门提醒 **无需** 再问「要不要发」 |
| 通道 | `jm-notify`（`$HOME/.joycode/skills/jm-notify/scripts/send_joyme.py --mode user`；项目内可回退 `.joycode/skills/jm-notify`；禁止 `../jm-notify`） |
| 文案 | 友好短讯：当前节点、要做什么、可选操作、引导回对话回复；详见 [`references/gate-notify-template.md`](./references/gate-notify-template.md) |
| 失败 | 对话中一句话说明失败原因，**不阻塞**闸门等待 |
| 区分 | `--notify-missing` 通知**发起人**补字段时，正式发送前仍须用户确认 |

执行顺序：① 对话展示闸门正文 → ② 调用 `jm-notify` 发提醒 → ③ 等待用户在对话中回复。

---

### 1.2 用户回复处理

**闸门回复即推进**
- 用户在闸门处回复后，必须根据回复内容推进到下一步
- 禁止重复询问同一个已确认问题
- 已问过且用户回答过的问题，不要再问

**信息不足时精确补问**
- 需要用户补充信息时，明确说明缺什么
- 给出选项（不要让用户自由发挥）
- 用户补充后立即继续流程（补问本身不等于确认闸门，但闸门仍须单独确认）

**信息补全约束**

| 阶段 | 补全策略 |
|-----|---------|
| 关键字参数 | 必须询问，无轮次限制（必需信息） |
| 问题标准化 | 最多追问 2 轮，之后基于现有信息继续，再开闸门「Bug确认」|
| 上下文分析 | 不追问，基于现有信息继续 |

---

### 1.3 输入类型识别

**识别类型后立即处理**

| 输入类型 | 处理方式 |
|---------|---------|
| **关键字** | 读取配置 → 输出一次选择提示 → 停止等待用户 |
| **异常** | 直接进入分析流程 |
| **问题描述** | 直接进入分析流程 |

**关键字处理流程**：
1. 读取配置 → `cat .harness/wiki/bug-fix/config.json`
2. 收集参数：
   - systemName：**必须询问**
   - env：**必须询问**
   - pin：**优先自动获取**（config.json 已保存值 > `git config user.name` > 询问用户）
3. 调用脚本 → 执行日志检索
4. 检查完整性 → 日志被截断时自动调用 `log_context.sh`
5. 保存配置 → 包括 pin（如本次从 git 获取或用户输入）到 `.harness/wiki/bug-fix/config.json`

## 二、Bug 类型约束

### 2.1 自动判断

**Bug 类型由 AI 根据输入信号自行判断，不需要询问用户。**

| 类型 | 信号 | 说明 |
|------|------|------|
| **code-error** | 报错、NPE、堆栈、错误码、日志ERROR | 代码层面的技术问题（缺陷） |
| **logic-deviation** | 预期不符、需求不一致、功能不对 | 需求理解偏差或实现与设计不一致（需求问题） |

详细判断规则参考：@stages/input-recognition.md

### 2.2 类型切换【流程切换】

定位过程中发现 Bug 类型与初始判断不一致时，允许动态切换，**但必须先经闸门「流程切换」确认**：
- `code-error` → `logic-deviation`：代码逻辑本身没错，但与需求不一致
- `logic-deviation` → `code-error`：代码实现与需求一致，问题是执行异常

**切换时必须开闸门「流程切换」，等待用户确认后再调整策略**

**切换后的流程调整**：

| 切换方向 | 流程调整 |
|---------|---------|
| → logic-deviation | 立即按需加载需求上下文，与用户确认预期行为 |
| → code-error | 继续按技术问题处理，无需加载需求上下文 |

### 2.3 logic-deviation 特殊处理

当 Bug 类型为 `logic-deviation` 时：
- **按需加载需求上下文**：检测 `.harness/changes/` 下是否有关联需求
- 何时加载：用户明确提到需求不一致、预期不符，或需要对照需求文档才能定位问题
- 如何加载：加载 `spec.html`（如存在）和 `design.html`（如存在）
- 与用户确认预期行为 vs 实际行为

### 2.4 Bug 类型对流程的影响

| Bug 类型 | 后续流程 |
|---------|---------|
| **code-error** | 按技术问题处理，定位根因 → 生成修复方案 |
| **logic-deviation** | 与产品确认需求 → 确定修复方向 → 生成修复方案 |

**logic-deviation 处理原则**：
- 需要产品/需求方确认后才能修改代码
- 可以先分析问题、定位根因，提供分析报告
- 询问用户：是否需要继续分析（即使不能立即修复）

## 三、错误处理约束

### 3.1 脚本错误处理

**脚本错误不跳过**

❌ **禁止行为**：
- 查看脚本源码
- 说"外部脚本有问题，我继续流程"
- 假装脚本执行成功
- 掩盖错误信息

✅ **强制行为**：
- 向用户报告错误，说明无法完成该操作
- 给出替代方案：
  - 手动提供信息
  - 基于已有信息继续
  - 稍后重试
- 明确说明影响（可能影响修复准确性）

---

### 3.2 升级机制

**快速通道升级时**
- 停止当前流程
- 回滚已修改的代码（如有）
- 转入完整流程
- 已完成工作作为输入参考
- 向用户说明升级原因
- **必须先经闸门「流程切换」确认**后再按完整流程继续

---

## 四、流程约束

### 4.1 问题处理

**单问题处理原则**
- 每次只处理单个问题
- 禁止批量处理多个问题
- 禁止批量修复

**原因**：
- 修改一个问题后，之前的分析可能失效
- 需要重新评估其他问题
- 避免相互影响

**问题队列管理**
- 必须从 Skill 层管理问题队列
- 问题处理完后必须询问是否继续
- 有待处理问题时，询问用户是否继续处理下一个

---

### 4.2 阶段执行

**必须按阶段顺序执行**
- 禁止跳过任何阶段直接生成修复代码
- 禁止跳过输入类型识别
- 禁止跳过问题分级判断
- 每个阶段必须产出标准化数据
- AI 不可自行决定下一阶段，必须由 SKILL.md 控制

**阶段特殊约束**
- 问题标准化阶段：只做标准化，不做判断
- 快速通道：必须经过安全检查

---

### 4.3 确认闸门策略

**原则**：根因（Bug原因）与修复方案**分开确认**，禁止把两者合并成一次确认后直接改代码。

**执行方式**：
1. 闸门「Bug列表」：锁定目标（多问题队列时先选定；单问题也须复述确认）
2. 闸门「Bug确认」：问题标准化 / 快速通道问题确认 / 详情对齐完成后确认理解
3. 非闸门阶段（上下文分析等）简要汇报并自动继续
4. 闸门「Bug原因」：根因分析完成后单独确认（可附带问题分级评估摘要，但不含详细修复方案）
5. 闸门「修复方案」：修复方案单独确认；通过后进入建分支，**仍禁止立刻改代码**
6. 闸门「建分支确认」：收集/确认 feature_branch（优先缺陷【分支名称】）；推荐 worktree（可不切主仓）；若「当前区直接改」则须 `ensure_checkout_branch`（干净默认切；脏区闸门后 stash 再切）；通过后才允许改代码
7. 闸门「提交确认」：上线检查完成（或合法跳过）后确认是否提交
8. 闸门「推送确认」：git commit 成功后确认是否 push（**可跳过**）；确认后按 `@stages/git-push.md` **先 pull 再 push**；冲突则 abort 提醒用户；跳过推送则跳过行云部署
9. 闸门「行云部署」：push 成功后确认是否行云部署（**可跳过**）
10. 闸门「流程切换」：类型或路径（快速通道↔完整流程）切换时确认
11. 闸门「服务评价」：统计收集后、上报前；必须输出 hb-choices 并停等

**闸门「Bug列表」输出格式**（单条已锁定时示例）：
```markdown
## 闸门「Bug列表」：锁定目标缺陷

{缺陷摘要表格}

## hb-choices
- 确认处理 {bug_code} | 确认
- 换另一条缺陷 | 换一条
- 先不修 | 先不修

回复方式：…
```

**闸门与流程步骤对应**（见 SKILL.md 流程表格）：

| 闸门 | 触发步骤 |
|------|---------|
| Bug列表 | 步骤 2 输入识别完成后（建立/锁定队列） |
| Bug确认 | 步骤 4（快速通道）或步骤 5（完整流程）完成后 |
| Bug原因 | 步骤 7 完成后；快速通道在步骤 10 改代码前须先给简要根因并开本闸门 |
| 修复方案 | 步骤 8 完成后；快速通道在步骤 9 前开本闸门 |
| 建分支确认 | 步骤 9 进入时（须已过修复方案；F/A 均必经） |
| 提交确认 | 步骤 12 上线检查完成（或合法跳过）后 |
| 推送确认 | 步骤 13 进入时（commit 已成功；可选跳过） |
| 行云部署 | 步骤 14 进入时（push 已成功；可选跳过） |
| 流程切换 | 类型切换或 F↔A 升级/降级时 |
| 服务评价 | 步骤 16 上报前（必须输出 hb-choices：好 / 还可以 / 差，并停等） |

**闸门「Bug原因」输出格式**：
```markdown
## 闸门「Bug原因」：根因确认

## 根因分析结果
{分析结论}

## 问题分级评估（如有）
{分级结论}

**修复方向（一句话）**：{...}

请确认：根因判断是否正确？
```

**闸门「修复方案」输出格式**：
```markdown
## 闸门「修复方案」：方案确认

## 修复方案
{详细方案 / 方案 A/B/C 对比}

请确认：是否按此方案修改代码？
- 确认执行 → 继续
- 需要修正 → {具体说明}
- 取消 → 停止流程
```

**复杂问题多方案时**：在同一闸门「修复方案」内完成「选择 A/B/C」+「确认执行」；未确认前禁止改代码。方案确认后须再开「建分支确认」，禁止合并。

**闸门「建分支确认」输出格式**：
```markdown
## 闸门「建分支确认」：创建修复分支

**缺陷**：{bug_code 或标题}
**目标功能分支**：{feature_branch}（优先【分支名称】）
**主仓当前分支**：{current_branch}；工作区：干净 / 有未提交改动
**拟操作（推荐）**：worktree 拉 fix（可不切主仓）

请确认：
1. **功能分支名**（必填，可预填【分支名称】须确认）
2. **修复分支名**（可选）：默认 fix/{bug_code}
3. **仓库路径**（若上下文不明确）

选项：
1. 确认建 worktree（不切主仓）→ aegis-fix-branch
2. 切到目标分支后直接改 → ensure_checkout_branch（脏区先 stash 决策）
3. 取消 → 停止，不改代码

## hb-choices
- 确认建 worktree（不切主仓） | confirm_worktree
- 切到目标分支后直接改 | checkout_direct
- 取消 | cancel
```

**闸门「提交确认」输出格式**：
```markdown
## 闸门「提交确认」

**验证结果**：{摘要}
**上线检查**：{通过 / 跳过（原因） / 有风险：…}
**拟提交**：{commit 草稿 / 文件列表}

请确认：是否提交？
```

**闸门「推送确认」输出格式**：
```markdown
## 闸门「推送确认」：是否推送到远程

**提交状态**：已 commit（{短 hash / 分支}）
**拟操作**：先 pull --rebase，再 push

请确认：
1. 确认推送 → 执行 pull + push
2. 跳过推送 → 跳过行云部署，进入治理沉淀
3. 稍后推送 → 等同跳过
```

**闸门「行云部署」输出格式**：
```markdown
## 闸门「行云部署」：是否部署

**提交状态**：已 commit 且已 push（{短 hash / 分支}）
**建议**：{建议环境或「待你指定」}

请确认：
1. 确认部署 → 调用 xingyun-deploy
2. 跳过部署 → 进入治理沉淀
3. 稍后部署 → 等同跳过
```

**推送执行约束**（闸门「推送确认」通过后）：
- 必须按 `@stages/git-push.md` 执行：先 `pull --rebase`（或等价 pull），再 `push`
- pull/push 冲突或非快进失败：立即 abort，提醒用户本地解决，**禁止**强制推送、禁止进入行云部署
- 用户解决后回复继续时，从 pull 重试
- 未过闸门「推送确认」禁止 pull/push；跳过推送则不得进入行云部署

**闸门「流程切换」输出格式**：
```markdown
## 闸门「流程切换」：类型/路径切换确认

**原判断**：{...}
**建议新判断**：{...}
**切换原因**：{...}
**策略变化**：{...}

请确认：是否按新判断继续？
```

**闸门「服务评价」输出格式**：
```markdown
## 闸门「服务评价」

**缺陷**：{bug_code}
**请对本次服务进行评价**

## hb-choices
- 好 | 好
- 还可以 | 还可以
- 差 | 差
```
输出后必须停止等待用户点击，禁止同一轮继续上报。

## 五、修复约束

### 5.1 修复原则

**详细规则请参考**：[`references/rules.md`](./references/rules.md)

核心原则：
- **最小修改原则**：只修改解决问题必须的代码
- **不做无关修改**：修复范围必须严格限定在当前问题
- **保持原有行为**：不得破坏已有业务行为
- **优先局部修复**：先定位，再修复，最后考虑优化

### 5.2 修复禁止行为

- 禁止在信息不完整时猜测问题原因
- 禁止只治标不治本的修复
- 禁止修复后不验证
- 禁止修复后不沉淀治理规则
- 禁止绕过快速通道安全检查
- 禁止未过闸门「修复方案」就修改业务代码
- 禁止未过闸门「建分支确认」就建 worktree 或改业务代码；禁止猜测 feature_branch
- 禁止有 worktree 时仍在主工作区改业务代码
- 禁止未过闸门「提交确认」就 git commit
- 禁止未过闸门「推送确认」就 pull/push；禁止跳过推送后仍进入行云部署；禁止 pull/push 冲突未 abort 仍继续
- 禁止未过闸门「行云部署」就触发行云构建/部署（跳过也须先开闸门明确选择）

### 5.3 修复强制行为

- 必须从 Skill 层管理问题队列
- 每次只处理单个问题
- 问题处理完后必须询问是否继续
- 有输入时必须执行输入类型识别
- 必须经过问题分级判断
- 快速通道必须经过安全检查
- 快速通道升级时必须回滚代码，并经闸门「流程切换」
- 必须按阶段顺序执行
- 修复后必须验证并沉淀治理规则
- 修复必须可验证、可回滚

## 六、确认点定义

### 必须确认的点

| 闸门 | 时机 | 目的 |
|------|------|------|
| Bug列表 | 锁定目标 Bug | 确认处理哪条 |
| Bug确认 | 问题标准化 / 快速通道问题确认完成 | 确认理解是否正确 |
| Bug原因 | 根因分析完成（或快速通道简要根因） | 确认根因正确 |
| 修复方案 | 修复方案生成后 / 改代码前 | 确认同意执行修复 |
| 建分支确认 | 修复方案通过后、改代码前 | 确认 feature 分支并建 worktree（或明确当前分支直接改） |
| 提交确认 | 上线检查完成（或合法跳过）后 | 确认同意提交 |
| 推送确认 | git commit 成功后 | 确认推送或跳过 |
| 行云部署 | push 成功后 | 确认部署或跳过 |
| 流程切换 | 类型或路径切换时 | 确认按新策略继续 |

**详细规则**：详见 §1.1、§4.3

### 确认方式

统一使用对应闸门标题（`## 闸门「{名称}」：...`），等待用户明确确认后再继续。非闸门步骤只做逐步汇报，不阻塞。

开闸门时须同步京 ME 提醒（§1.1.1）；文案模板见 [`references/gate-notify-template.md`](./references/gate-notify-template.md)。

- Skill 结束前必须执行统计收集
