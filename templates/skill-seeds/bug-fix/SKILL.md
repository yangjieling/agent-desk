# BugFix Skill

## ⛔ 强制执行规则（前置加载）

**本规则为最高优先级，必须在 Skill 执行前强制遵守**：

1. **加载红线规则**：必须先读取 @references/rules.md，遵守所有红线约束
2. **加载操作约束**：必须先读取 @constraints.md，遵守所有操作约束
3. **初始化执行日志**：创建本次执行的日志文件（步骤 1 执行前）

**违反以上规则 = 流程失败**

# 协作协议（全局强制）

## 逐步汇报

每完成一步，用 1～3 句话简要汇报，非闸门步骤自动推进。

## 确认闸门（必须等用户回复）

| 闸门 | 时机 | 未确认前禁止 |
|------|------|--------------|
| **Bug列表** | 锁定目标 Bug（队列选定 / 单条复述） | 进入排查 |
| **Bug确认** | 问题标准化 / 快速通道问题确认完成 | 深入根因 / 改代码 |
| **Bug原因** | 根因分析完成（或快速通道简要根因） | 出详细修复方案或改代码 |
| **修复方案** | 修复方案生成后 / 改代码前 | 修改业务代码 |
| **建分支确认** | 修复方案通过后、改代码前 | 未确认前禁止建 worktree / 改业务代码（须确认 feature_branch；推荐 worktree 可不切主仓；直接改须已在目标分支；脏区须用户决策后 stash） |
| **提交确认** | 验证通过且上线检查完成（或合法跳过）后 | git commit |
| **推送确认** | git commit 成功后 | 未确认前禁止 pull/push（可选：跳过推送） |
| **行云部署** | **push 成功** 后 | 未确认前禁止触发行云构建/部署（可选：跳过） |
| **流程切换** | 类型或路径切换时 | 按新策略继续 |
| **服务评价** | 统计收集结束、上报前 | 未评价前禁止调用上报脚本 |

**闸门京 ME 提醒（强制）**：每次开闸门时，对话展示确认内容的同时，用 `jm-notify` 给当前操作用户发个人消息（当前节点 / 要做什么 / 可选操作），用户可能不在对话页。发给自己的提醒无需再确认是否发送；失败不阻塞等待。文案见 `@references/gate-notify-template.md`。细则见 `@constraints.md` §1.1、§1.1.1、§4.3、§六。

**开闸门执行顺序**：① 对话展示闸门正文 → ② 若可用固定选项则输出 `## hb-choices`（见 `@constraints.md` §1.1.0）→ ③ 调用 `jm-notify` 发提醒 → ④ 等待用户在对话中回复 → ⑤ 用户确认后再推进。

## 执行记录机制（SKILL.md 统一管理）

### 核心原则

**SKILL.md 负责**：
- 在每个步骤执行前，记录步骤开始
- 在每个步骤执行后，记录步骤结束、结果、输出
- 管理执行日志文件的创建和更新
- 记录错误信息和回退信息

**stage 文件负责**：
- 只执行具体任务
- 输出标准化的结果（成功/失败、输出数据）
- 不需要记录执行日志

### 日志文件位置

`.harness/wiki/bug-fix/execution-log-{YYYYMMDD}-{HHmm}.md`


## 流程标记说明

**标记定义**：
- **F** = Fast Track（快速通道流程）：快速通道会经过此阶段
- **A** = Advanced Flow（完整流程）：完整流程会经过此阶段
- **N** = Necessary（必要）：所有流程必经的阶段
- **F/A** = 快速通道和完整流程都会经过此阶段

**标记作用**：
- 每个步骤执行完成后，**必须回到 SKILL.md** 查找下一阶段
- 根据当前流程类型（快速通道 F / 完整流程 A），找到标记匹配的下一阶段
- AI 不可自行决定下一阶段，必须由 SKILL.md 控制

**流程跳转规则**：
- 当前流程 = 快速通道 → 下一阶段找标记为 **F** 或 **N** 的步骤
- 当前流程 = 完整流程 → 下一阶段找标记为 **A** 或 **N** 的步骤

## 执行流程

**流程表格**：

| 执行顺序 | 功能 | 标记 | 文件位置 | 依赖数据 | 退出条件 | 输出数据 | 确认闸门 |
|---------|------|------|---------|---------|---------|---------|---------|
| 1 | 统计上报 | N | @stages/pre-bug-fix.md | 无 | 上报成功 | 调用记录 | — |
| 2 | 输入识别 | N | @stages/input-recognition.md | 用户输入 | 输入类型明确 | 输入类型、问题现象 | 完成后 → **Bug列表** |
| 3 | 问题分级 | N | @stages/problem-grading.md | 输入类型、问题现象 | 分级结果确定 | 流程类型（F/A） | 路径变更时 → **流程切换** |
| 4 | 问题确认 | F | @stages/fast-track.md | 问题现象 | 问题确认完成 | 确认的问题描述 | 完成后 → **Bug确认** |
| 5 | 问题标准化 | A | @stages/problem-standardization.md | 问题现象 | 标准化完成 | 标准化问题描述 | 完成后 → **Bug确认** |
| 6 | 上下文分析 | A | @stages/context-analysis.md | 标准化问题描述 | 上下文收集完成 | 项目上下文、调用链 | —（非闸门，汇报后自动继续） |
| 6.5 | 配置查询（按需） | F/A | @stages/config-query.md | 触发信号命中 / appCode | 查询完成或排除配置因素 | 配置项 / 连接串 / 结论 | —（横向能力，非闸门；根因/验证阶段按需插入） |
| 7 | 根因分析 | A | @stages/root-cause-analysis.md | 标准化问题描述、上下文 | 根因定位完成 | 根因定位、影响范围 | 完成后 → **Bug原因** |
| 8 | 修复方案生成 | A | @stages/fix-generate.md | 根因分析 | 方案生成完成 | 修复方案、测试方案 | 完成后 → **修复方案** |
| 9 | 创建修复分支 | F/A | @stages/create-fix-branch.md | 已确认的修复方案、仓库路径、【分支名称】 | 分支就绪或合法跳过隔离 | 分支摘要（fix_branch / worktree_path / 主仓是否切换） | 进入时 → **建分支确认**（优先 worktree；直接改须 ensure_checkout） |
| 10 | 修复实施 | F/A | @stages/fix-implementation.md | 修复方案 + 分支摘要 | 修复完成 | 修改清单 | 须已过 **修复方案** + **建分支确认**；有 worktree 时只在 worktree 改代码 |
| 11 | 验证 | F/A | @stages/verify.md | 修复方案、修改清单 | 验证通过 | 验证结果 | —（非闸门；通过后进上线检查） |
| 12 | 上线检查 | F/A | @stages/checklist-check.md | 验证结果、修改清单 | 检查完成或合法跳过 | 检查摘要 | 完成后 → **提交确认**（有风险须写入闸门文案）→ commit → **推送确认** |
| 13 | 代码推送 | F/A | @stages/git-push.md | 已 commit | push 成功或合法跳过 | 推送摘要 | 进入时 → **推送确认**（可跳过；确认后先 pull 再 push，冲突 abort） |
| 14 | 行云部署 | F/A | @stages/xingyun-deploy.md | 已 push | 部署完成或合法跳过 | 部署摘要 | 进入时 → **行云部署**（可跳过） |
| 15 | 治理沉淀 | N | @stages/governance.md | 验证结果、部署摘要（如有） | 沉淀完成 | 治理规则 | —（行云部署完成或跳过后执行；跳过推送时亦进入；若 workflow 后续节点为 `function-test`，需保留部署交接上下文） |
| 16 | 统计收集与上报 | N | @stages/statistics-collection.md | 全流程数据 | 上报完成 | 统计报告 | 上报前 → **服务评价**（好 / 还可以 / 差，须 hb-choices） |

**闸门推进规则**：
- 表中标注的闸门步骤：stage 产出完成后，由 SKILL.md **开闸门 + 发京 ME**，用户确认后再进入下一匹配步骤
- 非闸门步骤：简要汇报后自动继续
- 根因与修复方案必须分开确认，禁止合并成一次确认后直接改代码
- **修复方案与建分支确认必须分开**：方案通过后先开「建分支确认」，拿到 worktree（或用户明确跳过隔离）后才允许改代码

## 流程执行逻辑（SKILL.md 统一管理）

### 入口：步骤 1（统计上报）

**执行前操作**（SKILL.md 负责）：
1. 创建执行日志文件：`.harness/wiki/bug-fix/execution-log-{YYYYMMDD}-{HHmm}.md`
2. 写入基本信息：
   ```markdown
   # Bug-Fix 执行日志

   ## 基本信息
   - 开始时间：{当前时间}
   - 问题简述：{待填写}
   - 流程类型：{待填写}
   - 问题类型：{待填写}
   ```
3. 记录步骤开始：
   ```markdown
   ## 执行步骤

   ### 1. 统计上报
   - 开始时间：{当前时间}
   ```

**执行步骤**：
- 读取并执行 @stages/pre-bug-fix.md
- 获取输出结果

**执行后操作**（SKILL.md 负责）：
1. 记录步骤结束：
   ```markdown
   - 结束时间：{当前时间}
   - 耗时：{秒}
   - 结果：成功
   - 输出：上报成功
   ```
2. 决定下一步：
   - 成功 → 进入步骤 2
   - 失败 → 终止流程，记录失败原因

### 步骤 2-16 通用逻辑（SKILL.md 统一管理）

**每个步骤执行时，SKILL.md 必须**：

#### 1. 记录步骤开始
```markdown
### {步骤序号}. {步骤名称}
- 开始时间：{当前时间}
```

#### 2. 执行步骤内容
- 读取对应的 stage 文件
- 按照 stage 文件执行操作
- 获取输出结果（成功/失败、输出数据）

#### 3. 记录步骤结束

**成功**：
```markdown
- 结束时间：{当前时间}
- 耗时：{秒}
- 结果：成功
- 输出：{关键输出}
```

**失败**：
```markdown
- 结束时间：{当前时间}
- 耗时：{秒}
- 结果：失败
- 失败原因：{具体原因}
- 输出：{部分输出}
```

#### 4. 若本步对应确认闸门 → 开闸门（强制）

查流程表格「确认闸门」列：
1. 用 `## 闸门「{名称}」：...` 在对话展示确认内容（格式见 `@constraints.md` §4.3）
2. 按 `@references/gate-notify-template.md` 调用 `jm-notify` 发京 ME 提醒
3. **停止推进**，等待用户回复
4. 用户确认 → 记录闸门通过到执行日志 → 进入第 5 步
5. 用户修正 → 更新产出后**再次**开同一闸门（含再次发京 ME）
6. 用户取消/暂停 → 终止或回到闸门「Bug列表」

无闸门标注的步骤跳过本段。

#### 5. 决定下一步

**成功（且闸门已通过或本步无闸门）** → 查找流程表格，找到下一个步骤

**失败** → 根据失败类型决定：
- 终止流程
- 回退到指定步骤
- 等待用户确认

### 失败处理逻辑（SKILL.md 统一管理）

**步骤失败后，根据失败类型决定跳转**：

| 失败类型 | 跳转目标 | 日志记录 |
|---------|---------|---------|
| 理解问题 | 步骤 5（问题标准化） | 记录错误、回退信息 |
| 代码问题 | 步骤 7（根因分析） | 记录错误、回退信息 |
| 方案问题 | 步骤 8（修复方案生成） | 记录错误、回退信息 |
| 测试问题 | 当前步骤重试 | 记录错误、保留工作 |
| 其他问题 | 终止流程 | 记录失败原因 |

**跳转前必须**（SKILL.md 负责）：
1. 回滚代码（如果已修改）
2. 记录回退信息到日志：
   ```markdown
   ## 流程回退记录

   ### 回退 {序号}
   - 从步骤：步骤 {当前步骤}
   - 到步骤：步骤 {目标步骤}
   - 回退原因：{失败原因}
   - 已完成工作：{哪些工作需要保留}
   ```
3. 记录错误信息：
   ```markdown
   ## 错误记录

   ### 错误 {序号}
   - 发生步骤：步骤 {当前步骤}
   - 错误描述：{具体错误}
   - 错误原因：{为什么会出现这个错误}
   - 正确做法：{应该怎么做}
   - 回退到：步骤 {目标步骤}
   ```

---

### 回退后的处理（SKILL.md 统一管理）

**回退到指定步骤后**：
1. 使用已完成的工作成果（如适用）
2. 从目标步骤继续执行
3. 不重复执行已确认的步骤
4. 继续记录执行日志

## 流程跳转示例

### 示例 1：快速通道成功路径

```
SKILL.md：创建执行日志 → 记录步骤 1 开始
  ↓
步骤 1（统计上报）→ 执行成功 → SKILL.md：记录步骤 1 结束
  ↓
步骤 2（输入识别）→ 执行成功 → 开闸门「Bug列表」+ 京 ME → 用户确认
  ↓
步骤 3（问题分级）→ 执行成功（流程类型=快速通道）
  ↓
步骤 4（问题确认）→ 执行成功 → 开闸门「Bug确认」+ 京 ME → 用户确认
  ↓
改代码前：开闸门「Bug原因」+「修复方案」+ 京 ME → 用户确认
  ↓
步骤 9（创建修复分支）→ 开闸门「建分支确认」+ 京 ME → 用户提供 feature 分支 → 调用 aegis-fix-branch
  ↓
步骤 10（修复实施）→ 在 worktree 中改代码 → 执行成功
  ↓
步骤 11（验证）→ 执行成功
  ↓
步骤 12（上线检查 checkList）→ 执行或合法跳过
  ↓
开闸门「提交确认」+ 京 ME → 用户确认提交 → 在修复分支 / worktree 中 git commit
  ↓
步骤 13（代码推送）→ 开闸门「推送确认」+ 京 ME → 确认后先 pull 再 push（冲突 abort）；跳过则进治理沉淀
  ↓
步骤 14（行云部署）→ 开闸门「行云部署」+ 京 ME → 确认部署或跳过
  ↓
步骤 15、16 → 治理沉淀与统计
  ↓

```

## 升级规则

- 快速通道任一步骤发现复杂度超标 → **先开闸门「流程切换」**（含京 ME），用户确认后标记流程类型为 A，从当前步骤对应的完整流程步骤继续执行
- 升级映射：4 → 5
- 已完成的工作成果直接作为后续步骤的输入，无需重复执行
- 已确认过的闸门无需重复执行
- SKILL.md 在日志中记录升级信息

## 流程终止情况

- 步骤 5（问题标准化）判断为需求变更 → 终止流程，推荐使用需求开发流程
- 其他步骤失败且回退次数超过 3 次 → 终止流程，输出失败原因
- 用户取消修复 → 终止流程，记录用户取消原因

## 最终汇报生成（SKILL.md 统一管理）

**流程成功完成后，SKILL.md 负责**：

### 1. 统计执行数据
- 计算总耗时
- 统计执行步骤数
- 统计回退次数
- 统计错误次数

### 2. 生成问题记录
- 从日志中提取所有错误记录
- 格式化为"问题记录"格式

### 3. 生成经验教训
- 从错误记录中提取经验教训

### 4. 更新执行日志
追加到执行日志：
```markdown
## 最终汇报

### 执行统计
- 总耗时：{分钟}
- 执行步骤数：{数量}
- 回退次数：{数量}
- 错误次数：{数量}

### 问题记录（推送）
本次出现问题：
1. {错误描述}，原因是 {原因}
2. {错误描述}，原因是 {原因}

### 经验教训
- {经验教训 1}
- {经验教训 2}
```

### 5. 推送问题记录
- 将问题记录追加到 `.harness/wiki/bug-fix/issues.md`

### 6. 推荐代码审查
- 流程结束后，推荐用户使用 `code-review` skill
- 说明：代码审查是独立的质量保障环节，不在 bug-fix 流程内

### 7. Workflow 下游接续提示
- 若当前运行于 shared workflow，且后续节点为 `function-test`，则在 bug-fix 最后一轮总结中明确提示：
  - `已完成缺陷修复`
  - `如本次流程内已执行部署，测试步骤将自动接续`
  - `若测试入口信息仍缺失，下一步会继续向用户补问`
- 该提示是**补充说明**，不得替代 `## 部署交接上下文`

## 约束规则

**⛔ 强制要求：执行流程时，必须读取并遵守对应规则**：

| 使用场景 | 必须遵守的规则 |
|---------|---------------|
| 任何流程执行时 | @references/rules.md（红线规则：必须按流程执行、只做流程定义的事） |
| 任何代码修改时 | @references/rules.md（红线规则：最小修改、不做无关修改、保持原有行为） |
| 业务规则不明确时 | @references/rules.md（红线规则：不允许猜测、不允许假设） |
| 涉及支付/资金/权限等 | @references/rules.md（红线规则：高风险逻辑禁止直接修改） |
| 用户交互时 | @constraints.md（交互约束：逐步汇报、确认闸门、京 ME） |
| 开任一确认闸门时 | @constraints.md §1.1.1 + @references/gate-notify-template.md（必须发京 ME） |
| 上线检查时 | @stages/checklist-check.md + 独立 skill `.joycode/skills/checkList/SKILL.md`（`checkList-check`） |
| 配置 / DUCC / 数据源反查 | @stages/config-query.md（DUCC：`bug-fix/scripts/check_ducc_*.sh`；DB：转发 **db-query** skill） |
| 日志检索 | @stages/log-search-interface.md（亦可使用 **log-search** skill） |
| 建修复分支时 | @stages/create-fix-branch.md + 独立 skill `.joycode/skills/aegis-fix-branch/SKILL.md`（闸门「建分支确认」） |
| 提交后推送时 | @stages/git-push.md（闸门「推送确认」→ 先 pull 再 push；冲突 abort） |
| 行云部署时 | @stages/xingyun-deploy.md + 独立 skill `.joycode/skills/xingyun-deploy/SKILL.md`（可跳过；若 workflow 后续节点为 `function-test`，部署成功后必须输出 `## 部署交接上下文`） |
| Bug 类型判断时 | @constraints.md（Bug 类型约束：自动判断、类型切换须经「流程切换」闸门） |
| 执行脚本时 | @constraints.md（错误处理约束：脚本错误不跳过） |
| 统计上报时 | @constraints.md（统计约束：必须执行、数据完整） |

**规则说明**：
- **@references/rules.md** = 红线规则：能做什么、不能做什么的强制性约束
- **@constraints.md** = 操作约束：具体的交互规范、错误处理、统计要求

**执行要求**：
- 执行流程步骤时，**必须先读取红线规则**
- 只做流程定义的事，**禁止做额外的事**
- 可以多思考、多分析，但操作必须严格限定在流程定义范围内
