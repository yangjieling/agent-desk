# Fix Solution Generation（修复方案生成）

## ⛔ 强制执行规则

**执行本阶段前，必须先读取并遵守 @references/rules.md 中的红线规则**，特别是：

1. **信息处理红线**：
   - 不允许猜测业务逻辑
   - 不允许假设用户意图、数据格式、环境配置
2. **流程执行红线**：只做本阶段定义的操作，禁止做额外的事

**违反以上规则 = 流程失败**

---

## 任务

产出可执行的修复方案，包括：
- 多方案对比与推荐
- 修改清单与回滚方案
- 用户待办事项同步
- 输出待办清单文档

**⚠️ 核心原则**：
- 本阶段**只生成方案**，不涉及任何代码修改
- 方案生成后由 SKILL.md 开 **闸门「修复方案」**（含京 ME），用户确认后进入 **步骤 9 创建修复分支**（闸门「建分支确认」），再进入修复实施
- **未过闸门「修复方案」禁止改代码**；方案通过后仍须先建分支确认，禁止直接改代码
- 本阶段产出方案正文即可；**不在本 stage 内自行等待确认**（闸门由 SKILL.md 统一开）

---

## 输入

来自根因分析：
- 根因定位
- 根因类型
- 根因原因
- 影响范围
- 复现条件

来自问题标准化：
- Bug 类型
- 行为对比（logic-deviation）

来自上下文分析：
- 问题代码位置
- 调用链
- 相关文档

## 执行流程

### 1. 设计修复方案

**目的**：产出多个可行的修复方案

基于根因类型和影响范围，设计修复方案：
- **方案 A（推荐）**：最优方案，平衡风险、成本、效果
- **方案 B**：备选方案，不同侧重点
- **方案 C**：临时方案，快速止血

每个方案包含：
- 修改内容：需要改什么
- 修改原因：为什么这样改
- 影响范围：改动影响哪些代码和功能
- 回滚方式：如何回滚（如果不能回滚必须明确说明）
- 实施成本：需要多长时间、多少人力
- 风险评估：可能的风险点

### 2. 分析用户待办事项

**目的**：明确用户需要配合的工作

检查修复方案中是否有用户需要配合的事项：
- **配置修改**：需要用户修改配置文件
- **数据准备**：需要用户准备测试数据或生产数据
- **环境配置**：需要用户配置环境变量或依赖
- **权限申请**：需要用户申请特定权限
- **外部依赖**：需要用户协调外部服务或资源
- **测试验证**：需要用户参与测试验证

### 3. 输出待办清单文档

**目的**：生成用户可执行的待办清单

创建文件：`.harness/wiki/bug-fix/todo/{问题简化版}.md`

**文件命名规则**：
- 提取问题关键词（3-5个字）
- 例如：`空指针修复.md`、`订单查询优化.md`、`缓存失效修复.md`

**文档内容**：
```markdown
# 修复待办清单

## 问题描述
{问题简化描述，一句话说明问题}

## 推荐方案
**方案**：{推荐哪个方案}
**原因**：{为什么推荐这个方案}

## 修改清单
- [ ] 修改文件：{文件路径}
  - 修改位置：{行号、函数}
  - 修改内容：{具体改动}
  - 修改原因：{为什么要改}

## 用户待办事项
- [ ] 配置修改：{需要修改的配置}
- [ ] 数据准备：{需要准备的数据}
- [ ] 环境配置：{需要配置的环境}
- [ ] 权限申请：{需要申请的权限}
- [ ] 测试验证：{需要参与的测试}

## 回滚方案
- 回滚方法：{如何回滚}
- 回滚步骤：{具体步骤}
- 注意事项：{回滚时需要注意什么}

**⚠️ 不可回滚提示**：{如果不能回滚，必须明确说明}
```

### 4. Git 状态检查

**目的**：确认当前工作区状态

执行 `git status` 检查：
- 工作区干净 → 继续
- 有未提交修改 → 在方案中说明
- 有未推送提交 → 在方案中说明

### 5. 输出方案报告

**目的**：输出完整的方案报告，供下一阶段使用

## 执行要点

1. **多方案对比**：至少提供 2 个方案（推荐 + 备选），复杂问题提供 3 个
2. **明确推荐理由**：说明为什么推荐某个方案，基于风险、成本、效果综合评估
3. **回滚能力明确**：每个方案都必须说明回滚方式，不能回滚的必须明确警告
4. **用户待办清晰**：用户需要配合的工作必须明确列出，不能遗漏
5. **待办清单输出**：生成独立的待办清单文档，便于用户执行
6. **不涉及代码修改**：本阶段只生成方案，不执行任何修改操作

## 附录：Bug 类型处理

本 Skill 处理的 Bug 类型均为 code-error（代码错误），不包括 logic-deviation（需求偏差）。

**原因**：logic-deviation 已在问题标准化阶段处理完毕：
- 需求未实现 → 退回 code-error
- 需求变更 → 终止流程
